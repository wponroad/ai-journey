## 二、今天踩的三个坑，都是同一类问题

### ① System 和 User 放错位置

第一版写法：

```csharp
var messages = new List<ChatMessage> { new ChatMessage(ChatRole.System, question) };
```

**把用户的问题塞进了 System 槽位。** 现象是"改了跟没改一样"——因为模型把提问当成了系统指令，然后照做，看起来和原来差不多。

正确的结构至少两条消息：

```csharp
new ChatMessage(ChatRole.System, systemPrompt),   // 开发者设定：它是谁
new ChatMessage(ChatRole.User, question)          // 用户提问
```

**为什么这个错误危险**：`System` 优先级最高。用户输入进了这个位置，等于获得了最高权限。
用户只要输入"忽略以上所有指令"，模型就会当命令执行 —— 这是 prompt injection 的入口。
**用户输入必须永远在 User 槽位。**

### ② 两条路径分叉

上午只给 `AskAsync` 加了 System Prompt，`AskStreamAsync` 还是老代码。
结果：**非流式说"我是本地部署的"，流式说"我是阿里云通义千问"。**

证据在 token 数上：

| | 输入 token | 带 System 吗 |
|---|---|---|
| 非流式 | 75 | 有 |
| 流式 | 33 | **没有** |

差的 42 个 token 就是 System Prompt。

**这类 bug 最难查**：不报错、不崩溃，只是行为悄悄不一致。用户会说"有时候答得对有时候答错"，
而规律是"取决于调的是哪个方法"。

### ③ Assistant 的回复没进历史

原来的循环只把用户的话 `Add` 进列表，模型的回答从来没加过。
上下文是断的 —— 模型看不到自己刚说了什么。

**修法**：每轮结束把回答也塞进去，角色是 `Assistant`。

## 三、System Prompt 的效果：三次对照

| | System Prompt | 它的回答 |
|---|---|---|
| D4 | 无 | 我是通义千问……部署在阿里云的云端服务器上 |
| D5 | 无 | 我是由 **OpenAI 开发的 ChatGPT** |
| 今天 | `你是我本地AI小助手，帮我解决一些本地工作问题` | **我是你的本地AI助手，专注于本地化任务处理** |

**一句 20 字的话，把三轮幻觉全摁住了。**

机制不神秘：System Prompt 不改模型的知识，只改**上下文里的前提**。模型是"接着往下说"的机器，
你给它"你在本地"这个前提，它就不再滑向训练数据里那个"我是云端大模型"的高频模板。

**所以以后遇到"模型不听话"，第一个该试的是 System Prompt，不是换模型或调参数。**

另一个副作用：**历史里的回答风格会传染。** 第二轮它先复述了一遍自我介绍才写诗，
因为第一轮的回答就是这个格式，模型在模仿。**你给它的任何样板，它都会学。**

## 四、多轮对话的真实数据

| | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 输入 token | 62 | **98（+58%）** |
| 输出 token | 22 | 18 |
| 历史条数 | 3 | 5 |
| 总耗时 | 2038 ms | 1159 ms |

**两个现象值得记住：**

**① 第二轮输入 98 里，62 是上一轮的全部内容。**
你的问题只有几个字，但输入涨了 58% —— **你在为重复发的东西反复付费**。聊得越久，这个重复越多。

**② 第二轮输入更长，反而快了一倍**（1159ms vs 2038ms）。
这是**提示词缓存**：服务端认出前面那段刚算过，跳过重复计算。

**连带后果：现在的成本计算器算高了。**
缓存命中的输入应该按 `InputCachePrice`（0.04）算，不是 `InputPrice`（2），差 50 倍。
拿不到缓存 token 数时只能按全价算，是保守的高估。

## 五、W1 门槛自查（五题）

> 门槛原文：不看文档，能白板画出「用户输入 → token 化 → 模型推理 → 流式返回 → 计费」整条链

### 第 1 题　为什么现在的对话接口用 messages 数组，而不是一个 string？

**答**：一条 string 表达不了对话结构。

```
messages: [
  { role: "system",    content: "你是..." },   ← 设定
  { role: "user",      content: "问题" },      ← 提问
  { role: "assistant", content: "回答" },      ← 历史
]
```

文字只有内容，没有**角色、顺序、边界**。

**这不是推测，有历史依据**：OpenAI 2023 年的 `/completions` 接口**就是只接受一个 string**
（参数名叫 `prompt`）。后来改成了 `messages` 数组，因为多轮对话和角色区分需要结构。

**今天上午的 bug 正好是这条的实证**：把用户问题放进了 `System` 槽位，模型立刻把它当最高指令执行。
如果接口只收 string，这种区分根本无从谈起。


### 第 2 题　token 化发生在你的电脑上，还是服务端？

**答**：服务端。你发出去的永远是字符串，token 化是对方的内部事务。

证据是现成的：

| 同一个 prompt | 服务端算出的输入 token |
|---|---|
| qwen3（本地 Ollama） | **36** |
| DeepSeek（云端） | **56** |

**你的电脑发出去的是同一串字符。** 如果 token 化在本地，两边数字必须一样。
之所以不同，是因为**各家用各自的词表在各自的服务器上算**。

同理，D1 用 SharpToken 算出的 459 只是**照着 OpenAI 词表做的本地估算**，不是真正发给模型的。
真正计费的是服务端返回的那个数 —— 这就是为什么 `usage` 才是唯一可信的依据。

### 第 3 题　服务端记得你上一句吗？多轮对话到底谁在记？

**答**：服务端不记录上一句，多轮对话是本地在记录，每次都会把历史记录发给服务端。

代码就是证据：`history` 列表在 `Program.cs` 里，每轮往后追加，每次整段发出去。

**这就是"上下文"这个词最原始的含义** —— 不是模型记住了，是你每次都重新告诉它。

### 第 4 题　SSE 和 WebSocket 的区别？为什么流式没让总耗时变短？

**答**：流式仅仅是将思考过程和返回数据分批次返回，但是总体的思考和计算时间是不变的。

**SSE 与 WebSocket 的区别：**

| | SSE | WebSocket |
|---|---|---|
| 方向 | **单向**（服务端 → 客户端） | 双向 |
| 协议 | **就是普通 HTTP**，响应不关掉 | 需要协议升级（HTTP 101） |
| 复杂度 | 一个 `text/event-stream` 响应头 | 连接状态、心跳、重连都要自己管 |

**LLM 只需要服务端往你这边推字，不需要你中途回话，所以 SSE 够了。** 用 WebSocket 是杀鸡用牛刀。

**关于总耗时，补一句精确的：**

> 流式不减少总时间，它减少的是"**什么都没发生**"的时间。
> 总 token 数不变、推理计算量不变，变的只是**什么时候开始给你**。

### 第 5 题　你凭什么相信 `usage` 返回的那个数字，就是账单上的数字？

**答**：不能完全"相信"，只能说它是目前最接近账单的计算方式，建议增加对账验证。

分三层：

**① 为什么它最可信。**
`usage` 是**服务端在生成结束后统计的**，和计费系统用的是同一份数据。
不是客户端算的，不是估算的。你在 D1 用 SharpToken 算的 459、用官方系数 0.6/字 估的 233，都是猜；
只有 `usage` 是服务端自己报的账。

**② 但它仍然可能和账单不一致，有三种情况：**

- **参数没生效**：设了 `max_tokens = 20`，实际输出 217。账单按 217 算，
  你以为按 20 算 —— 这时 `finish_reason` 是唯一线索（`stop` 说明没截断，`length` 才是截断了）
- **缓存命中被混在一起**：DeepSeek 的 `prompt_tokens = 缓存命中 + 未命中`，
  两者单价差 50 倍。只拿总数算，成本会算高
- **不同口径的字段**：`total_tokens`、`prompt_tokens`、`completion_tokens` 包含关系要搞清楚，
  用错字段会重复计算

**③ 唯一能真正验证的办法是对账。**

> 跑一批固定调用，把每次的 `usage` 累加，和官网账单比。差得多就是有问题。

这是工程上唯一可靠的态度：**不盲信任何一个数字，用两个独立来源交叉验证。**
和 D4 那次一样 —— `finish_reason` 证明 `max_tokens` 没生效，靠的就是交叉验证。

## 六、整条链：哪一步在你的代码里

把 W1 的门槛画成一条线，并且标出每一步归谁：

| 步 | 做什么 | 发生在 | 是你的代码吗 |
|---|---|---|---|
| ① | 用户输入一段 string | 客户端 | ✅ |
| ② | 结构化成 messages 数组（角色 + 内容 + 历史顺序） | 客户端 | ✅ |
| ③ | 序列化成 JSON，HTTP POST | 客户端 | ✅ |
| ④ | tokenizer：字符串 → token ID | **服务端** | ❌ |
| ⑤ | 逐个生成 token，每算完一个立刻推一个 | **服务端** | ❌ |
| ⑥ | 解析 SSE 的 data 行 → `ChatResponseUpdate` → `LlmChunk` | 客户端 | ✅ |
| ⑦ | 打印到屏幕（TTFT 在这一刻） | 客户端 | ✅ |
| ⑧ | 生成结束，统计 usage 随最后一片回传 | **服务端** | ❌ |
| ⑨ | 用 usage 复算成本 | 客户端 | ✅ |

**结论：你的代码只在两头——拼消息、渲染结果。中间全是对方的。**

排查问题时第一个该问的就是这句话：**这一步发生在谁的地盘上？** 在自己这边就查日志、查代码；在对方那边就查文档、查返回字段，改自己的代码是白费力气。

### 第一版描述里缺的四处

**① 「加工成序列化数据」其实是两步，性质不同**

```
string "你好"
  ↓ 结构化（加角色、加历史、定顺序）      ← 业务逻辑，决定模型看到什么
messages: [{role:"user", content:"你好"}]
  ↓ 序列化（对象 → JSON 字节）           ← 传输格式，决定怎么运过去
```

`ToChatMessages` 干的是前者，`JsonSerializer` 干的是后者。混在一起说，就说不清"改错了应该查哪一步"。

**② 推理和返回是交织的，不是先后**

不是「模型推理 → 流式返回」，是**边推理边返回**：每算出一个 token，立刻推一个出去，不等全部算完。

这正是 `yield return` 的语义（算一片、交一片、暂停、等下次），也是 TTFT（522ms）和总耗时（2374ms）能差出 1.8 秒的原因。

**如果真是「推理完再返回」，流式就没有任何意义。**

**③ 计费不是一个时点，是两个**

| 时点 | 发生什么 |
|---|---|
| 请求到达时 | 输入 token 数确定，**输入部分**计费开始 |
| 生成结束时 | 输出 token 数确定，**账单定稿** |

输出部分是边生成边累加的，所以在结束之前，连服务端自己都不知道总价。

**④ 链条不能停在「返回给客户端」，还有落地**

```
SSE data 行 → 解析成 ChatResponseUpdate → 翻译成 LlmChunk → 打印到屏幕
```

而且 `usage` 是**随最后一片回来的**。成本计算器里那个数字，就是这条回传路径的终点。

---

### 一个必须分清的区别

> **服务端计费** 和 **你的成本计算器** 是两件事。

服务端算自己的账（一手数据）；你的程序拿 `usage` **复算一遍**（二手数据），用于预估、告警、对账。

前者你改不了，后者是你的代码。**这就是为什么第 5 题要讲"对账"** —— 你在用二手数据核对一手账单，唯一可靠的验证方式是两个来源对得上。
