# W02 · Day 1　结构化输出：从字符串到强类型对象

> 日期：2026-11-09（周一）　模型：qwen3:8b（本地 Ollama）　项目：HelloLlm
> 目标：让模型的输出能被程序解析成对象，而不是只能给人读。

---

## 一、今天的分界线

W1 之前，模型的输出一直是**给人看的**：你读它，判断它对不对。

从今天起，输出要**给程序用**。程序不能"大概理解"，只能精确解析。

**这就是结构化输出要解决的问题：把自由文本变成有明确结构的对象。**

---

## 二、四条路径，代价完全不同

| 路径 | 做法 | 保证什么 | 代价 |
|---|---|---|---|
| ① 纯 prompt | 提示词里写"请输出 JSON" | 什么都不保证 | 会带 markdown 包裹、多余解释、字段乱起名 |
| ② JSON 模式 | `response_format: json_object` | 保证是**合法 JSON** | 不保证字段名、字段类型 |
| ③ 严格 Schema | `response_format: json_schema` | 保证**结构和字段** | provider 支持不一致 |
| ④ 工具调用 | function calling | 结构最稳 | 要按工具格式设计 |

**其中 ② 和 ③ 的区别是今天最容易混的一点：**

> `json_object` 保证"能 parse"，`json_schema` 保证"字段对"。
> 前者只解决语法，后者才解决结构。

这条表就是 W2 第一问（"结构化输出有哪几种实现路径？各有什么代价"）的答案框架。

---

## 三、`ChatResponseFormat` 是什么

**它不是格式转换工具，是请求参数。** 你设了它，MEAI 在 HTTP 请求里加一个 `response_format` 字段，服务端看到后约束自己的输出。

| 写法 | 底层字段 | 保证 |
|---|---|---|
| `ChatResponseFormat.Text`（默认） | 不传 | 自由文本 |
| `ChatResponseFormat.Json` | `{"type": "json_object"}` | 合法 JSON |
| `ChatResponseFormat.ForJsonSchema<T>()` | `{"type": "json_schema", ...}` | 按类型结构输出 |

**关键原理：`json_schema` 是"约束解码"——不是请求它输出 JSON，而是在采样时把不合 schema 的 token 概率归零。**

一个是建议，一个是禁止，可靠性差一个量级。

**但它只是"请求"，不是"保证"**：provider 不支持就静默忽略，你还是会拿到自由文本。

## 四、今天踩的四个坑

### ① 参数被 `null` 短路了

第一版把 `ResponseFormat` 写进了 `BuildOptions`：

```csharp
private static ChatOptions? BuildOptions(LlmSettings? settings)
{
    if (settings is null) return null;     // ← 整段被跳过
    ...
    ResponseFormat = ChatResponseFormat.Json
}
```

而调用是 `llm.AskStreamAsync(history)` —— 没传 `settings`，所以直接 `return null`，**`ResponseFormat` 那行一次都没执行过**。

**根因**：这个短路是 D4 为了"不覆盖服务端默认值"写的，理由没错；但它把"没有调用级参数"当成了"什么都不发"。

**解法**：把格式定义成调用级参数（`LlmSettings.OutputFormat`），而不是服务端固定配置。

### ② 类型不匹配：`"128.5"` vs `128.5`

同一个 prompt，只改 system 里十几个字，输出在三种形态之间来回跳：

| system prompt | 模型的输出 |
|---|---|
| "只输出 JSON…字段名必须是…" | `"amount": 128.5` |
| "你是信息抽取器…" | `"amount": "128.5"` |
| 再改一次 | `"amount": "128.5 元"` |

**`ParsedOrder.Amount` 是 `decimal`，给它字符串就抛异常。**

这说明：**prompt 不是"指令"，是"影响因素"。** 它只能提高概率，不能保证结果。

### ③ 带单位的字符串：`"128.5 元"`

`NumberHandling = JsonNumberHandling.AllowReadingFromString` 只能吃**纯数字形式的字符串**，`"128.5 元"` 多了两个字符，还是失败。

**清洗能力有极限：**

| 模型输出 | 能救吗 | 靠什么 |
|---|---|---|
| `128.5` | ✅ | 原生 |
| `"128.5"` | ✅ | `AllowReadingFromString` |
| `"128.5 元"` | ✅ | 正则 / 自定义 converter |
| `"一百二十八块五"` | ❌ | 救不了 |

**所以最优解不是把兜底写多强，是让模型一开始就给对。兜底是保险，不是主路。**

### ④ 假成功：解析没报错，字段全是空

这一条最严重。

```
ParsedOrder { OrderNo = , Status = , Amount = 0 }
```

5 次全是这个结果，而且**一次异常都没抛**。

**根因在自己的代码里**：

```csharp
JsonSerializer.Deserialize<ParsedOrder>(extract.Text)   // 没传 jsonOptions
```

`JsonSerializerOptions` **默认区分大小写**。模型给的是 `"orderNo"`，record 属性叫 `OrderNo`，对不上 → 解析器当成"字段不存在"，**静默跳过**，返回全默认值的对象。

> **解析成功 ≠ 拿到数据。**
> 抛异常至少你知道出事了；假成功会让程序拿着空对象继续跑，最后把空订单发给客户。

**排查顺序（以后照这个来）：**

1. 打印原始 JSON，看键名到底是什么
2. 和 record 的属性名逐个对比
3. 大小写不一致 → `PropertyNameCaseInsensitive = true`
4. 下划线/中文键名 → `[JsonPropertyName("order_no")]`，或者回到 prompt 里约束

**模型输出错和解析器配置错是两件完全不同的事。** 今天这个属于后者，代价是半小时。

---

### 补充验证：Ollama 认不认 `json_schema`（当天 20:35 实测）

写到这里时这条还没验证。最后补了一组对照：同一句话、同一个模型，三组各跑 5 次。

| 组 | 传的东西 | 5 次结果 |
|---|---|---|
| A | 什么都不传 | 键名全是**中文**：`订单号` / `状态` / `金额` |
| B | `json_object` | **和 A 完全一样**，还是中文键名 |
| C | `json_schema`（`strict: true`） | **5 次全部正确**：`orderNo` / `status` / `amount`，且 `amount = 128.5` 是数字 |

**三个结论：**

**① Ollama 支持 `json_schema`，效果是决定性的。** 5 次零波动。

**② `json_object` 只保证「能 parse」，对字段名毫无约束。** B 组和 A 组结果一模一样 ——
那个参数只做了「输出合法 JSON」这一件事，结构完全交给模型自由发挥。

**③ 没有 schema 时，模型会用中文键名。** 因为 prompt 是中文的。
这种情况下 `PropertyNameCaseInsensitive` 救不了（中文和英文不是大小写问题），
只能靠 prompt 里显式写字段名 —— 而那个，今天已经证明不稳定。

> **优先级：`json_schema` > prompt 里写字段名 > 什么都不做。**
> 前者是硬约束，中间是软建议，后者等于放弃控制。

**这条结论推翻了前面第 ② 小节的建议**：原先说「先用 `json_object` 跑通，别卡在 schema 上」，
是因为不确定 Ollama 支不支持。验证之后，应该直接上 schema。

## 五、prompt 四段式

今天最后采用的写法（比"请输出 JSON"有效得多）：

```
你是信息抽取器。从用户给的文字里提取订单信息，只输出一个 JSON 对象。

字段定义：
- orderNo：字符串，订单编号，只保留编号本身
- status：字符串，订单状态
- amount：数字类型，只保留数值，不要单位，不要引号

示例：
输入：订单 B20260101，已签收，共 99.9 元
输出：{"orderNo":"B20260101","status":"已签收","amount":99.9}

只输出 JSON，不要解释，不要 markdown 代码块。
```

**四个部分缺一不可：**

| 部分 | 作用 |
|---|---|
| 角色 | 让它进入"抽数据"状态，而不是聊天 |
| 字段定义 | 逐个说类型和约束，尤其 `amount` 要明说"数字、不要单位" |
| **示例** | **最重要**，模型是模仿机器，不是规则机器 |
| 禁止项 | 不要解释、不要代码块 |

**关于示例的三条经验：**

1. **一个示例胜过十行规则。** 写"amount 必须是数字类型"它可能理解成"数字的字符串"；但看到 `"amount":99.9` 没有引号，它会照抄形态
2. **示例数据必须和真实数据不同**（B20260101/99.9 vs A20261109/128.5），否则模型可能把示例抄回来
3. **示例要展示你最怕出错的那个字段**：最怕 amount 带单位，示例里就放"共 99.9 元"配上干净的 `99.9`

## 六、三层防线（`try-catch` 只是第一层）

```csharp
try
{
    var order = JsonSerializer.Deserialize<ParsedOrder>(extract.Text, jsonOptions);

    // 第二层：解析成功但字段全空
    bool isEmpty = order is null
        || (string.IsNullOrEmpty(order.OrderNo)
            && string.IsNullOrEmpty(order.Status)
            && order.Amount == 0);

    if (isEmpty) { /* 打印原始输出，报警 */ }
}
catch (JsonException ex)
{
    // 第一层：JSON 本身坏了
    Console.WriteLine($"原始：{extract.Text}");
    Console.WriteLine($"原因：{ex.Message}");
}
```

| 层 | 抓什么 |
|---|---|
| `try-catch (JsonException)` | JSON 格式坏了、类型不对 |
| `isEmpty` 检查 | 解析成功但字段一个没读到 |
| 打印原始输出 | 前两层都没抓到，让人眼能看 |

**只写 try-catch 是不够的。** 它只能抓语法错误，抓不住"名字没对上"这种静默失败。

## 七、结论

1. **结构化输出有四种路径**，从"什么都不保证"到"结构最稳"，代价递增
2. **`json_object` 只解决语法，`json_schema` 才解决结构**，两者不能混
3. **prompt 是影响因素，不是指令**——同一个 prompt 跑几次，输出形态会跳
4. **参数不生效的第一步检查，是确认它有没有发出去**（又被 null 短路了一次）
5. **解析成功 ≠ 拿到数据**，必须做空值检测
6. **兜底的四层顺序**：序列化选项（零成本）→ 重试 → 修正提示 → 正则，不能反
