## 一、今天的转折：从「能跑」到「能验证」

前五天写的每个东西都"能跑"，但**没法证明它稳定**。

手动敲十条问题，跑到第三条就记不清前面跑的是什么；出了问题也只能靠回忆。**这不是工程，是试用。**

今天做的是把它变成**可以重复执行的验证**：

```
dotnet run
  1  对话模式
  2  批量测试（10 个用例，自动判成败）
  0  退出
```

## 二、CLI 的结构：三个文件分工

| 文件 | 职责 | 行数量级 |
|---|---|---|
| `Program.cs` | 读配置、建对象、启动 | ~80 |
| `ChatCli.cs` | 菜单 + 交互 + 批量 + 判定 | ~220 |
| `TestQuestion.cs` | 10 个用例 + 运行记录 | ~60 |

**`Program.cs` 只剩组装**——这是 D2 那条原则的延续：程序入口负责"知道所有人"，业务逻辑放在能被单独看懂的类里。

### 关键：两种模式共用一个 `AskOnce`

```csharp
private async Task<RunRecord> AskOnce(string id, string question)
{
    var messages = new List<LlmMessage>
    {
        new() { Role = LlmRole.System, Content = _systemPrompt },
        new() { Role = LlmRole.User, Content = $"/no_think {question}" }
    };

    var reply = await _llm.AskWithToolsAsync(messages, _settings, maxSteps: 5,
        trace: line => { record.Steps++; Console.WriteLine(...); },
        onCalls: calls => record.ToolCalls.AddRange(calls));

    record.Answer = reply.Text;
    record.InputTokens = reply.InputTokens;
    ...
}
```

**手动问一句和批量跑一遍，走的是完全相同的代码路径。** 如果两条路分开写，你会在批量里测出问题、手动却复现不了。

### 为了统计改的两处

**① `AskWithToolsAsync` 加了 `onCalls` 回调**

把"调了哪些工具、参数是什么"以 `ToolCallTrace` 回传。**不解析 `trace` 字符串**——解析自己打印的日志是种坏味道。

**② 多轮用量累加**

原来只返回最后一轮的 `Usage`，但**账单是按每一次 API 调用算的**：

```csharp
long totalIn = 0, totalOut = 0, totalCached = 0;
// 每轮 response.Usage 累加，最后用累加值构造 LlmReply
```

**只记最后一轮，成本会被严重低估**（D4 实测：两轮 967 token vs 单轮 550）。

## 三、10 个用例怎么设计

**核心：不同类型都要有，不是同一个问题问 10 遍。**

| # | 问题 | 考察点 | 期望调工具 |
|---|---|---|---|
| 1 | 订单 A20261109 现在什么状态 | 单工具 | ✅ |
| 2 | SKU-001 还有多少库存 | 单工具 | ✅ |
| 3 | SKU-001 买 5 件总共多少钱 | 双工具并行 | ✅ |
| 4 | 我最近那单怎么样了 | **串行依赖**（先查号再查详情） | ✅ |
| 5 | 订单 A99999 是什么状态 | 查不到，不能崩 | ✅ |
| 6 | SKU-002 买 3 件多少钱 | 已售罄 | ✅ |
| 7 | SKU-003 我要 20 件 | 超库存 | ✅ |
| 8 | 那个 199 块钱的东西还有货吗 | **模糊指代** | ✅ |
| 9 | 你能做什么 | **不该调工具** | ❌ |
| 10 | 订单 A20261110 什么状态 | 另一笔订单 | ✅ |

**第 8 和第 9 题最容易挂**：
- 8 要模型自己从"199 块钱"推断是 SKU-003
- 9 如果它硬调工具，说明工具描述太"贪"，什么场景都想用

## 四、三层判据：什么算失败

没有判据，"0 失败"只能靠人眼看。

| 层 | 失败条件 | 判据字段 |
|---|---|---|
| 程序层 | 抛异常、崩溃 | `record.Error is not null` |
| 调用层 | 该调工具却没调 / 不该调却调了 | `ExpectTool` vs `ToolCalls.Count` |
| 结果层 | 回答里没有该有的内容 | `ExpectContains` |

```csharp
if (c.ExpectTool && r.ToolCalls.Count == 0)
    → "没有调用工具（可能在凭印象回答）"

if (!c.ExpectTool && r.ToolCalls.Count > 0)
    → $"不该调工具，却调了 {r.ToolCalls.Count} 次"

if (c.ExpectContains is not null && !r.Answer.Contains(c.ExpectContains))
    → $"回答里没有「{c.ExpectContains}」"
```

**`ExpectContains` 是最弱的一环**——它只能检查"答案里有没有这个字符串"，检查不了语义正确。但对本项目够用，因为它能抓出最常见的故障：**模型没查数据就编了答案。**

## 五、实测：第一轮 10 次

| # | 步数 | token | 成本（等价云端） |
|---|---|---|---|
| 1 | 2 | 1165 | **0.000857** |
| 2 | 2 | 1138 | 0.000336 |
| 3 | 2 | 1170 | 0.000395 |
| 4 | **3** | **1753** | 0.000505 |
| 5 | 2 | 1199 | 0.000494 |
| 6 | 2 | 1160 | 0.000388 |
| 7 | 2 | 1164 | 0.000387 |
| 8 | 2 | 1151 | 0.000339 |
| 9 | **1** | **543** | 0.000182 |
| 10 | 2 | 1157 | 0.000365 |

**总成本 0.004249 元。**

三个数据值得看：

**① 第 9 题步数 1、543 token** —— 没调工具直接答，判据里 `ExpectTool = false` 起了作用。

**② 第 4 题步数 3、1753 token** —— 唯一的串行依赖，成本最高，和 D4 的 1532 量级一致。

**③ 第 1 题和第 2 题：token 几乎一样（1165 vs 1138），成本差 2.5 倍（0.000857 vs 0.000336）**

## 六、一个意外：token 和成本不成正比

**原因是缓存。**

第 1 题是这场测试的第一次调用，缓存是冷的，几乎全部按未命中单价算（2 元/百万）；从第 2 题开始，system prompt 和 4 个工具定义都被缓存命中，单价降到 0.04 元/百万，差 50 倍。

> **同一个问题问两次，第二次便宜一半以上。**
> 放到真实产品里：**冷启动用户的成本是活跃用户的两三倍。**

这也是为什么"按 token 数估成本"会错——**必须看 `usage` 里的缓存命中数**（D5 已经处理）。

## 七、5 轮 × 10 用例 = 50 次全过

在 VS 里连跑 5 轮，每轮 10 个用例，**全部通过**。

**这比门槛要求的"连续 10 次"强得多**——它说明系统是**稳定**的，不是运气好一次。

### 但这个数字有一个边界

50 次全过，是 **qwen3:8b + 这 10 个用例**的成绩。

换成云端模型、或者换一批更刁钻的问题（多订单、中文数字、超长文本、歧义句），失败率会变。

**它证明的是「当前场景稳定」，不是「系统永远可靠」。**

**但这正是工程上能拿出去说话的东西**——不是"我觉得挺稳"，是"5 轮 50 次、0 失败、用例在这、代码能复现"。

---

## 八、结论

1. **能跑 ≠ 能验证**：批量模式 + 明确判据，才让"稳定性"变成一个可测量的数
2. **两种模式必须共用同一个 `AskOnce`**，否则批量测出的问题手动复现不了
3. **多轮用量要累加**，只记最后一轮会严重低估成本
4. **用例要覆盖不同类型**：单工具、多工具、串行、查不到、边界、模糊、不需要工具
5. **判据分三层**：程序没崩 → 工具调用符合预期 → 答案里有该有的内容
6. **token 数和成本不成正比**：缓存命中率可以让同样的 token 便宜 2.5 倍
