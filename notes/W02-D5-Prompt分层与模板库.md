# W02 · Day 5　Prompt 分层与模板库

> 日期：2026-11-13（周五）　项目：HelloLlm
> 目标：把散在代码里的 prompt 抽出来，做成可版本管理的模板。

---

## 一、为什么要把 prompt 从代码里拿出来

在这之前，三处 prompt 全是硬编码的字符串：

| 位置 | 内容 |
|---|---|
| `Program.cs` | 订单抽取的 system prompt（四段式） |
| `Program.cs` | 对话的人设 |
| `Program.cs` | 工具调用的 system prompt |

**问题不在"写在代码里"，在于：**

- 改一句约束要翻代码、重新编译
- 没法对比"上一版是不是更好"
- 出问题时不知道线上跑的是哪个版本

---

## 二、四层结构

| 层 | 回答什么问题 | 修改频率 |
|---|---|---|
| `role` | 你是谁、干什么 | 很少 |
| `constraints` | 什么必须做、什么不能做 | **最频繁** |
| `format` | 输出长什么样 | 中等 |
| `examples` | 具体案例 | 中等 |

**分层的核心理由：四层的修改频率完全不同。**

约束层天天调（加一条"不许编造"、改一句措辞），角色层几乎不动。混在一个大字符串里，**改约束时很容易顺手碰到示例——而示例一动，模型行为变化很大**。

分层之后，改约束只动 `constraints` 数组，示例一个字不碰。

### 拼接顺序：角色 → 约束 → 格式 → 示例

**示例放最后是有意的**：它离用户消息最近，模型的模仿效果最强。

如果把示例放在角色后面、中间隔着一堆约束，模仿效果会打折——**模型对"最近看到的样板"最敏感。**

## 三、JSON 模板与版本号

`prompts/order-extract.json`：

```json
{
  "id": "order-extract",
  "version": "1.0.0",
  "updatedAt": "2026-11-13",
  "note": "从文本里抽取订单信息，配合 json_object / json_schema 结构化输出",
  "layers": {
    "role": "你是信息抽取器。从用户给的文字里提取订单信息。",
    "constraints": [
      "只输出一个 JSON 对象，不要任何解释",
      "不要用 markdown 代码块包裹",
      "amount 只保留数值，不要单位，不要引号",
      "原文里没有的信息留空，绝不编造"
    ],
    "format": "字段定义：\n- orderNo：字符串，订单编号\n- status：字符串，订单状态\n- amount：数字\n\n输出形状：{\"orderNo\":\"string\",\"status\":\"string\",\"amount\":number}",
    "examples": [
      {
        "input": "订单 B20260101，已签收，共 99.9 元",
        "output": "{\"orderNo\":\"B20260101\",\"status\":\"已签收\",\"amount\":99.9}"
      }
    ]
  }
}
```

### `version` 不只是给人看的

三个用途：

1. **日志追溯**：每次调用记 `"prompt": "order-extract@1.0.0"`，效果变差时能定位到具体版本
2. **回滚**：v1.0.1 出问题，改回 v1.0.0 就行
3. **A/B 对比**：两个版本并存，跑同一批输入比结果

`PromptTemplate.ToString()` 返回 `"order-extract@1.0.0"`，直接能打进日志。

### 模板文件要进 git

**它不是配置，是代码的一部分。** prompt 改了、效果变了，必须有历史可查。

## 四、加载器

三个类分工：

| 类 | 职责 |
|---|---|
| `PromptTemplate` | 对应一个 JSON，提供 `Build()` 组装成字符串 |
| `PromptLayers` / `PromptExample` | 四层的数据结构 |
| `PromptLibrary` | 扫目录、按 id 取、查重 |

`Build()` 的核心就是把四层按顺序拼起来，每层之间空一行。

**不做热加载。** 改 JSON 要重启程序完全可以接受——等你真的需要频繁调到"不能重启"的程度再说，现在做就是过度设计。

## 五、两个坑

### ① 创建的模板文件的属性要设置如果较新则复制

**这个我最开始就漏了**，漏了的表现是运行时抛 `prompt 目录不存在`，而 C# 代码本身完全正确——怀疑加载器的路径拼接，查半天。

**加上后，模板文件才会跟着编译输出走。**

### ② 模板 id 重复时直接报错，不静默覆盖

今天真实撞到的：`prompts/` 目录里同时存在两个文件，`id` 都是 `order-extract`：

```
Uninitialized exception. System.InvalidOperationException: 模板 id 重复：order-extract
```

**这是故意的设计。** 如果加载器默默用后者覆盖前者：

- 你以为改的是 A 文件，实际运行的是 B 文件
- 两个文件内容不同时，行为差异无法解释
- 这种问题能查一整天

**"同名直接报错"是把问题挡在启动阶段**，代价是要处理一次麻烦，收益是永远不会遇到那个查不动的问题。

### 顺带：两个人的同一份 prompt，差异在约束层

合并时发现，自己写的那版约束只有三条，少了一条 **"amount 只保留数值，不要单位，不要引号"**——而那正是 D1 踩过的坑（`"128.5 元"`）。

**这说明约束层是最容易漏的一层**，因为它记录的是"踩过的坑"，不是"显而易见的要求"。

## 六、验证

### 组装结果

```
你是信息抽取器。从用户给的文字里提取订单信息。

约束：
- 只输出一个 JSON 对象，不要任何解释
- 不要用 markdown 代码块包裹
- amount 只保留数值，不要单位，不要引号
- 原文里没有的信息留空，绝不编造

字段定义：
- orderNo：字符串，订单编号，只保留编号本身
- status：字符串，订单状态
- amount：数字

输出形状：{"orderNo":"string","status":"string","amount":number}

示例：
输入：订单 B20260101，已签收，共 99.9 元
输出：{"orderNo":"B20260101","status":"已签收","amount":99.9}
```

**四层分界清晰，一眼能看出每段在干什么。**

### 抽取结果

输入：`订单号 C20261225，状态待付款，金额 88 元`

输出：

```json
{"orderNo":"C20261225","status":"待付款","amount":88}
```

**`amount` 是数字，没有单位、没有引号** —— 和手写 prompt 的行为一致，说明拆分没有改变语义。

## 七、结论

1. **分层不是为了好看，是因为四层的修改频率不同** —— 改约束不该碰示例
2. **示例放最后**，离用户消息越近模仿效果越强
3. **`version` 是给日志和回滚用的**，不是装饰
4. **模板文件进 git**，它是代码不是配置
5. **csproj 的 `CopyToOutputDirectory` 必配**，否则运行时读不到
6. **同名 id 直接报错**，把问题挡在启动阶段，比运行时行为诡异好得多
