# W02 · Day 2　失败率对照：两组都是 0

> 日期：2026-11-10（周二）　模型：qwen3:8b（本地 Ollama）　项目：HelloLlm
> 目标：拿到 `json_object` 和 `json_schema` 的失败率对比，为兜底提供依据。

---

## 一、实验设计

同一个 prompt、同一个模型、同一段输入，两组各跑 10 次：

| 组 | 设置 |
|---|---|
| A | `OutputFormat = Json`（`response_format: json_object`） |
| B | `OutputFormat = JsonSchema, SchemaType = typeof(ParsedOrder)` |

**判定标准分三种，不能只看"有没有抛异常"：**

| 结果 | 含义 |
|---|---|
| ✅ 成功 | 反序列化成功，且字段有值 |
| ⚠️ 空值 | **解析通过但字段全默认值**（名字没对上，假成功） |
| ❌ 异常 | 反序列化抛 `JsonException` |

---

## 二、结果：零差异

| 组 | 成功 | 空值 | 异常 |
|---|---|---|---|
| A `json_object` | **10** | 0 | 0 |
| B `json_schema` | **10** | 0 | 0 |

每一行的输出完全一样：

```
✅ ParsedOrder { OrderNo = A20261109, Status = 已发货, Amount = 128.5 }
```

**预期中的差异没有出现。**

---

## 三、为什么零差异 —— 真正的变量不是格式

昨天验证 `json_schema` 时，同样的两组，结果差异巨大：

| | system prompt | A 组（json_object） |
|---|---|---|
| 昨天 | `你是信息抽取器。只输出 JSON。` | 键名全是中文：`订单号` / `状态` / `金额`，**0/5 可用** |
| 今天 | 四段式（角色 + 字段定义 + 示例 + 禁止项） | **10/10 全对** |

**两次唯一的区别是 prompt。**

所以结论要改写：

> **真正的变量是 prompt 质量，不是 `json_object` 和 `json_schema`。**

---

## 四、四组拼图，现在齐了

| prompt | 格式 | 结果 | 数据来源 |
|---|---|---|---|
| 弱 | `json_object` | ❌ 中文键名，0/5 | 昨天 |
| 弱 | `json_schema` | ✅ 5/5 | 昨天 |
| 强 | `json_object` | ✅ 10/10 | 今天 A 组 |
| 强 | `json_schema` | ✅ 10/10 | 今天 B 组 |

**完整的结论：**

> **prompt 是第一道防线，schema 是第二道。两者不是替代关系，是叠加关系。**
>
> - prompt 写好了，`json_object` 就够
> - prompt 写差了，只有 schema 能救
> - 两个都做好，才有 10/10

**这也解释了为什么昨天那个"优先级：schema > prompt 字段说明"说得不够准。**
准确的说法是：**schema 是兜底，prompt 是主路。兜底比主路可靠，但主路走通了就不需要兜底。**

---

## 五、一个必须警惕的结论：0 失败不代表系统稳

**失败率 0%，只代表这个任务太简单。**

今天抽的输入：

> "订单号 A20261109，状态已发货，金额 128.5 元。"

**这是结构化抽取里最容易的一类：**

1. 有明确标签（"订单号"、"状态"、"金额"）
2. 格式规范（编号、状态词、数字+单位）
3. 单一实体，没有歧义

换成下面这些，失败率立刻就不是 0：

| 输入类型 | 难点 |
|---|---|
| "上周三那个客户又下单了，还是那个价" | 隐含信息、需要上下文 |
| 2000 字需求文档里抽 5 个字段 | 长文本、信息分散 |
| "一百二十八块五" | 中文数字 |
| 一封邮件里有两个订单 | 一对多，要返回数组 |

> **先制造问题，再解决问题。**
> 今天验证的是"简单任务不会失败"，它是有效的实验结论，
> **但不能被误读成"我的系统很稳"。**

---

## 六、实验设计上的一个失误

今天本想看"格式"的差异，但 prompt 同时也变了（从弱到强）。

**结果是两个变量一起动，无法分离贡献。**

更干净的设计应该是四组：

```
强 prompt × json_object
强 prompt × json_schema
弱 prompt × json_object
弱 prompt × json_schema
```

四组跑完，才能算出"prompt 贡献了多少、schema 贡献了多少"。

**今天的补救**：正好昨天做过弱 prompt 的那两组，四组数据凑齐了。
但那是运气，不是设计 —— **下次做对照实验，先想清楚有几个变量。**

---

## 七、结论

1. **强 prompt + 任意格式 = 10/10**，`json_object` 已经足够
2. **弱 prompt 时，只有 schema 能救**（昨天：0/5 vs 5/5）
3. **prompt 是主路，schema 是兜底**，两者叠加最稳
4. **判"成功"要看字段有没有值**，不能只看有没有抛异常（假成功最危险）
5. **0 失败先怀疑任务太简单**，别急着下"系统稳定"的结论
