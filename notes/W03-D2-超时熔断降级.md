# W03-D2　超时 + 熔断 + 降级

> 2026-11-17　目标：模型挂了不返回报错，而是走规则兜底，并且整条链路有时间上限
> 一句话结论：**这三个策略不能单独看，它们的参数是一份预算；配错了不会报错，只会"看起来在工作、实际永远不触发"。**

## 一、三个组件回答三个不同的问题

| 组件 | 它回答的问题 | 时间尺度 |
|---|---|---|
| 超时 | 这次调用最多等多久 | 秒级 |
| 熔断 | 对方是不是已经挂了，还值不值得试 | 分钟级 |
| 降级 | 全都失败时给用户什么 | — |

**不是同一个问题的三种解法，是三个层次。**

## 二、分层顺序

```
降级 Fallback            最外层：全失败 → 规则兜底，用户看不到报错
  └ 总时长超时 100s        含重试在内的总预算
       └ 重试 4 次          指数退避 + 抖动（W3-D1）
            └ 熔断器        连续失败到阈值就打开，之后直接拒绝
                 └ 单次超时 10s
                      └ 真实调用
```

`Add` 的顺序就是**从外到内**，和读图一致。

### 熔断为什么必须在重试内层

| 位置 | 后果 |
|---|---|
| 熔断在**外层** | 重试 4 次全失败，熔断器只看到 **1 次**失败。要 4 轮用户请求才可能开，而每一轮都在往死掉的服务上打 4 次 |
| 熔断在**内层** | 每次重试都经过它，失败计数快速累积。一旦打开，后续重试被 `BrokenCircuitException` 直接短路，**一次网络请求都不发** |

省的不只是时间，还有钱——每次调用都是真金白银的 token。

### 超时为什么有两个

- **单次超时**（内层）：一次调用最多等 10 秒，防止某一次卡死
- **总时长超时**（外层）：含重试在内最多 100 秒

只有单次超时的话：4 次重试 = 40 秒起步，还不算退避。**总时长是给用户的承诺，单次超时是给单次调用的约束。**

## 三、坑一：`new TimeSpan(30000)` 是 3 毫秒

第一次配超时时直接报错：

```
The field Timeout must be between 00:00:00.0100000 and 1.00:00:00.
```

原因：

```csharp
new TimeSpan(30000)      // 30000 tick
                         // 1 tick = 100 纳秒 → 3 毫秒，低于 Polly 的 10ms 下限
```

`TimeSpan` 内部就是一个 `long`，单位是 tick。**只有一个参数的构造函数，那个参数就是 tick，不是毫秒。**

| 写法 | 实际值 |
|---|---|
| `new TimeSpan(30000)` | 3 毫秒 |
| `new TimeSpan(0, 0, 30)` | 30 秒（时, 分, 秒） |
| `TimeSpan.FromSeconds(30)` | 30 秒 ✓ |

> **和 W1 那个「每百万 token」是同一类错误：单位没写在字面上，就一定会错。**
> 凡时间用 `FromSeconds`，凡金额用 `decimal` 且显式除 1_000_000。

## 四、坑二：`TimeoutRejectedException` 不声明就不重试

现象：单次超时到了之后，重试一次都没发生，异常直接冒出去。

根因是**两个东西被当成了同一个**：

| | HTTP 408 | Polly 超时 |
|---|---|---|
| 谁产生的 | **服务端**返回一个响应 | **客户端**主动断开连接 |
| 异常类型 | `HttpRequestException` | **`TimeoutRejectedException`** |
| 有响应体吗 | 有 | **没有** |

代码里写的 `.Handle<HttpRequestException>(ex => ex.StatusCode is ... RequestTimeout ...)` 里的 `RequestTimeout` 是 **HTTP 408 状态码**，跟“本地等太久”毫无关系。

修法是显式加一行：

```csharp
.Handle<TimeoutRejectedException>()
```

> 一句话记：**`HttpRequestException` 是别人告诉你的失败，`TimeoutRejectedException` 是你自己判定的失败。不声明“我自己判定的也算失败”，Polly 就不会重试它。**

**还没完**：`TaskCanceledException` 那条要加条件，否则总超时取消时还会再试一轮：

```csharp
.Handle<TaskCanceledException>(ex => !ex.CancellationToken.IsCancellationRequested)
```

## 五、坑三：超时 / 次数 / 总时长是一份预算

一次真实的错误配置：

```
单次 12s + 3 次重试 + 总 30s
12 × 3 + 退避(1+2) = 39 > 30    ✗
```

第 3 次重试**根本跑不到**，总超时早就把它掐了。`MaxRetryAttempts = 3` 在这里是个假配置。

正确算法：

```
单次超时 × (重试次数 + 1) + 退避总和 ≤ 总超时
```

`12s 单次 + 30s 总` 的正确解：

| 步骤 | 累计 |
|---|---|
| 第 1 次 | 12s |
| 退避 | 13s |
| 第 2 次 | 25s |
| 退避 | 27s |
| 第 3 次 | 只剩 3 秒，必被掐 |

→ 只能 `MaxRetryAttempts = 1`（共 2 次尝试）。

> **这三个数字不是独立参数，是一份预算的分配。改任何一个，另外两个都要重算。**

还有一条：`12 + 18 = 30` 这种“正好相等”的配置不能写，实际会因为调度延迟和取消传播而被提前掐断。**留 2~3 秒余量。**

## 六、坑四：采样窗口必须盖住一次请求的实际耗时

熔断器配好了，日志也显示 4 次失败，但**死活不打开**。

算一下时间轴：

| 事件 | 累计 |
|---|---|
| 第 1 次 429（瞬时） | 0s |
| 等 1.1s + 第 2 次超时 | 11.1s |
| 等 0.7s + 第 3 次超时 | 21.8s |
| 等 2.1s + 第 4 次超时 | **33.9s** |

而 `SamplingDuration = 30` 秒。

**第 4 次失败发生时，第 1 次失败已经被滑出统计窗口。** 窗口内样本不足 `MinimumThroughput`，Polly 宁可不动。

Polly 的规则是：**样本数 < `MinimumThroughput` 时不评估**，避免基于太少数据误判。

修法：

```
SamplingDuration ≥ 单次请求最坏耗时 × 你希望几次请求后熔断
```

改成 90 秒后立刻生效。

### 附带一条：熔断阈值要和重试次数一起算

`MinimumThroughput = 4` 和「1 次原始 + 3 次重试 = 4 次调用」数值完全相等，意味着**一次失败的用户请求就足以打开熔断**。

| 想要的效果 | MinimumThroughput |
|---|---|
| 1 次请求就熔断 | 4（= 1 × 4 次尝试） |
| 3 次请求才熔断 | 12 |
| 5 次请求才熔断 | 20 |

**它们乘在一起才是样本量。**

## 七、降级：不是道歉

最容易做错的版本：

```csharp
return "抱歉，服务暂时不可用，请稍后再试。";
```

**那不是降级，那是换个说法报错。**

### 降级的分级

| 层级 | 做什么 | CLI 能不能做到 |
|---|---|---|
| 完整结果 | 规则答出一样的答案 | ✅ |
| 部分结果 | 只答出一部分 | ✅ |
| 缓存结果 | 返回上次类似答案 | 以后做 |
| 道歉 | 什么都答不了 | 兜底 |

模型在这类任务里干的事就两件：**识别意图 + 抽参数**。订单号是 `[A-Z]\d{8}`，SKU 是 `SKU-\d{3}`，正则比模型稳，而且永远不会挂。

```csharp
private string RuleBasedAnswer(string question)
{
    var orderNo = Regex.Match(question, @"[A-Z]\d{8}").Value;
    if (orderNo.Length > 0) return _orderService.GetOrder(orderNo);

    var sku = Regex.Match(question, @"SKU-\d{3}").Value;
    if (sku.Length > 0) return _orderService.GetStock(sku);

    return "智能助手暂时不可用。你可以直接说订单号（如 A20261109）或商品编号（如 SKU-001），我按规则帮你查。";
}
```

**连兜底都要告诉用户“现在还能做什么”。**

### 为什么不用 Polly 的 `AddFallback`

`FallbackAction` **拿不到用户原始的问题**，只拿得到异常。而规则兜底的第一步就是正则匹配，必须知道问了什么。

绕过去要往 `ResilienceContext` 里塞 messages——为一个业务决策做数据搬运，不值。

> 原则：**策略层管「失败了怎么办」，业务层管「失败时给用户什么」。**

### 只兜「服务挂了」这一类

```csharp
private static bool IsServiceDown(Exception ex) => ex switch
{
    BrokenCircuitException => true,
    TimeoutRejectedException => true,
    HttpRequestException => true,
    _ => false,
};
```

400 参数错、401 key 无效、自己的 `NullReferenceException` **都不兜**。

> 兜底会让它们变成一句「服务暂时不可用」，**然后你再也不会去修它了。**

### 降级必须显式标注

`LlmReply.IsFallback = true`，界面打印 `[降级·规则兜底]`。

| 用处 | 不标的后果 |
|---|---|
| 界面提示 | 用户以为模型在工作，实际只是正则 |
| 计费 | 降级成本为 0，混进正常统计会拉低均值 |
| 监控 | **降级率飙升 = 模型全挂了，但系统看起来一切正常** |

> **降级做得越好，故障越难被发现。**

## 八、今天最重要的发现：计费黑洞

### 现象

熔断触发那次，`usage` 全是空的：

```
[degrade] 没有产生 token 消耗（请求没真正发出去）
token 输入  / 输出  | 等价云端成本  元
```

但前面**三次“放行”的真实调用都超时了**——模型可能已经算了 3 秒、生成了 200 个 token、服务端已经计费，然后 10 秒到点被掐断。

### 根因：超时的请求根本没有 response

```csharp
var response = await _pipeline.ExecuteAsync(...);   // ← 超时在这里抛异常
if (response.Usage is { } u) { ... }                // ← 从来没执行到
```

**`usage` 是响应体里的字段。响应没完成，就没有响应体，就没有 usage。**

### 三种失败，账单可见性完全不同

| 故障 | 有响应吗 | 有 usage 吗 | 可能已计费吗 |
|---|---|---|---|
| 429 | ✅ | 通常有或明确没有 | 一般不计 |
| 500 | ✅ | 通常没有 | 一般不计 |
| **超时** | **❌** | **❌** | **可能已经计了** |

> **超时是唯一一种「钱可能花了、而你完全不知道」的失败。**

所以那句日志的措辞要改准确：

```
❌ 没有产生 token 消耗
✅ 没有收到 token 统计 —— 超时的请求可能已产生费用，客户端无从得知
```

### 三层解法

| 层 | 做法 | 靠谱程度 |
|---|---|---|
| ① 日志诚实 | 措辞改成「可能已计费，无从得知」 | 让人知道有洞 |
| ② 估算输入侧 | 输入 token 是确定的（prompt 固定，tokenizer 数一遍），超时按输入价记下界 | 不精确但有依据 |
| ③ 服务端记账 | 请求带 `request-id`，服务端记账、客户端对账 | **唯一正确** |

③ 也回答了 W2 那个待答问题「凭什么相信 usage」——**答案是：不相信任何一方，用两个独立来源交叉验证。**

## 九、让用量穿过异常边界（实现细节）

降级时要把“已经花掉的钱”记上，但 `totalIn/totalOut` 原来是 `AskWithToolsCoreAsync` 的**局部变量**——异常一抛，它们跟着方法栈一起消失。

改法：把统计装进一个可变对象，从外层传进去。

```csharp
var usage = new UsageAccumulator();          // 外层创建
try { return await AskWithToolsCoreAsync(..., usage); }
catch (...) when (IsServiceDown(ex))
{
    // usage 里还留着前面几轮的数字
    InputTokens = usage.IsEmpty ? null : usage.Input,
    Amount = usage.IsEmpty ? null : CalcAmount(usage.Input, usage.Output, usage.Cached),
}
```

**这不是代码风格问题，是生命周期问题。** 局部变量的存活止于方法返回——而恰恰是失败的那一次，最需要知道前面花了多少。

一个判断要分清：

| 场景 | usage | 含义 | 记成 |
|---|---|---|---|
| 熔断短路 | 全 0 | 请求没发出去，真没花钱 | `null`（没算） |
| 第 1 轮成功、第 2 轮超时 | Input 513 | **钱花了，答案没拿到** | 513 + 金额 |

**`0` 和「没拿到」是两回事。**

## 十、实测数据（熔断完整触发这一次）

配置：`failTimes = 1`（只第 1 次注入 429，后面都是真实调用超时）、单次 10 秒。

```
[flaky] 第 1 次 → 429
[retry 1] 等 1.2s
[flaky] 第 2 次 → 放行 → 10s 超时
[retry 2] 等 0.6s
[flaky] 第 3 次 → 放行 → 10s 超时
[retry 3] 等 2.5s
[flaky] 第 4 次 → 放行 → 10s 超时
[circuit] 打开                          ← 4 次失败，阈值达成
[retry 4] 等 1.7s
[degrade] BrokenCircuitException        ← 第 5 次请求被短路，没发出去
[degrade] 没有产生 token 消耗（实际是「没收到统计」）
AI > 订单 A20261109：已发货，金额 128.50 元  [降级·规则兜底]
耗时 66288 ms
```

### 两个关键观察

**① `[retry 4]` 之后立刻被熔断拦住，这是熔断在干活**

```
本该发生的第 5 次 10 秒超时，被省掉了。
```

熔断的价值不是“少一次失败”，是“**少一次白等 10 秒 + 少一笔可能的费用**”。

**② 理论耗时 36 秒，实际 66 秒**

`1.2 + 10 + 0.6 + 10 + 2.5 + 10 + 1.7 = 36s`，但显示 66288ms，差 30 秒。

推测原因：**Polly 的 Timeout 是协作式取消**——它发出取消信号，但底层 HTTP 请求要过一会儿才真的断开，本地 Ollama 那边可能还在继续生成，把下一次调用也拖慢了。

验证方法：单次超时改成 3 秒，看 4 次加起来是否接近 12 秒。远大于就是取消延迟。

**这个数字很重要**——它决定了“超时”这个保护在真实环境里到底管不管用。

## 遗留

- [ ] 总超时 100s / 单次 10s / 重试 4 次 = 预算严重不匹配（10 × 5 + 退避 > 100）
- [ ] 单次超时 10 秒 < 模型响应时间，导致每次尝试都必然超时、白花钱
- [ ] `Question 5`：66 秒 vs 36 秒的差额没验证
- [ ] 降级时输入 token 的估算（解法②）没做
- [ ] `FlakyChatClient` 缺 `failAfter` 参数（造不出「第 1 轮成功、第 2 轮失败」的场景）
- [ ] **`AskStreamAsync` 仍然没有 Polly 保护**（W3-D1 遗留，今天没补）
