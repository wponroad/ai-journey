# W01 · Day 5　成本计算器

> 日期：2026-11-06（周五）　模型：qwen3:8b（本地）/ deepseek-flash（云端）
> 目的：按 token 算钱。看起来是一行乘法，实际有一个必踩的坑。

---

## 一、核心公式，以及「百万」这个坑

```
金额 = 输入token / 1_000_000 × 输入单价
     + 缓存命中token / 1_000_000 × 缓存单价
     + 输出token / 1_000_000 × 输出单价
```

**单价是「元 / 百万 token」，而一次调用的 token 数是个位到几千。**

这两者差六个数量级，所以除法的位置决定了结果差 1000 倍：

| 写法 | 实际含义 | 错在哪 |
|---|---|---|
| `token × 单价` | 把单价当成「每个 token」 | 结果大 100 万倍 |
| `token / 1_000 × 单价` | 当成「每千 token」 | 结果大 1000 倍 |
| `token / 1_000_000 × 单价` | ✅ 正确 | — |

**为什么这个错特别隐蔽：** 算出来的数字量级不对，但程序不报错、不抛异常，
只是账单对不上。而且前期调用量小，金额都是 `0.0002` 这种，肉眼看不出差 1000 倍。

### 两个配套细节

**① 用 `decimal`，不用 `float` / `double`。**
金额要参与累加（一次会话几十轮、一个月几万次），二进制浮点的误差会累积成真实的账目差异。
`LlmReply.amount` 原来是 `float?`，改成了 `decimal? Amount`。

**② 显示时折算成「分」。**
`0.001012 元` 没人有感觉，`0.1012 分` 才有。程序里两个都打。

## 二、实现：三个设计决定

| 决定 | 理由 |
|---|---|
| 算在 `LlmService` 里，不放 `Program` | 成本和耗时、token 数一样，是「这次调用的结果」，不是界面的事 |
| `CostCalculator` 收 `ModelOptions`，不自己读配置 | 和 `IChatClient` 一个道理：依赖从外面递进来 |
| 算不出来返回 `null`，不返回 `0` | `0` 会被读成「这次免费」，`null` 才是「没算」 |

`CalcAmount` 的三个前提：**有计算器 + 有输入数 + 有输出数**，缺一个就返回 `null`。
因为 `Usage` 在某些 provider 上可能压根不给。

### 时段折扣

配置里的规则是「星期 + 时间段」，只有两个都命中才按原价：

```
星期在 UnDiscountWeek 里  且  时间落在 UnDiscountTime 的任一区间
    → 原价
否则
    → 乘 Discount
```

实现用 `TimeSpan.TryParse("9:00")` 解析时间，**左闭右开** `[9:00, 12:00)`，
所以 12:00 整点算空闲时段。

`(int)DayOfWeek` 是 **周日 = 0，周一 = 1 … 周六 = 6**，和配置里 `[1,2,3,4,5]` 正好对应。

### 本地怎么算

**计价永远读 `CloudModel` 那一节的价格。**

- 调云端时，算出来的就是实际成本
- 调本地时，算出来的是「**这一次如果走云端要花多少**」

所以输出写成：`本地实际 0 元 | 等价云端 0.000216 元`。

不显示 0 的原因：**本地一直跑，你永远不知道自己省了多少钱。**

## 三、验证：手算和程序对上了

非流式：输入 56、输出 239，当前空闲（0.5 折），单价 输入 2 / 输出 8（元每百万）。

```
56  / 1,000,000 × 2 × 0.5 = 0.000056
239 / 1,000,000 × 8 × 0.5 = 0.000956
                      合计 = 0.001012 元
```

程序输出 `0.001012 元（0.1012 分）` —— **完全一致。**

流式：输入 56、输出 262 → `0.000056 + 0.001048 = 0.001104 元`，也一致。

**手算是必须的一步。** 程序算错了它不会告诉你，只有手算才能发现。

## 四、意外收获：本地 vs 云端同问对照

同一个 prompt，两家跑出来：

| | 本地 qwen3:8b | 云端 deepseek-flash |
|---|---|---|
| **输入 token** | **36** | **56** |
| 输出 token（非流式） | 45 | 239 |
| 输出 token（流式） | 54 | 262 |
| 成本（非流式） | 0.000216 元（等价） | 0.001012 元（实际） |
| TTFT | 384 ms | 522 ms |
| 正文首字 | 384 ms | **2259 ms** |

### ① tokenizer 差异有真实数据了

**同样的文字，qwen3 数出 36 token，DeepSeek 数出 56 token，差 55%。**

D1 那条结论「token 数由 tokenizer 决定，不由文字决定」，当时只能用 cl100k 和官方系数间接对比，
现在有了同场景的直接对照。

### ② TTFT 和正文首字第一次分开

- 本地：TTFT 384 = 正文首字 384，**相等**，因为第一片就是正文
- 云端：TTFT 522 < 正文首字 2259，**差 1737 ms**，因为第一片是思考内容

**这一刻 TTFT 这个指标才有意义** —— 用户 522 毫秒就看到东西在动，不用干等 2.3 秒。

## 五、发现：思考内容回传了

流式输出里出现了模型的自言自语：

> 我们需要回答中文。用户要求：先用一句话介绍自己……我需要说明我是云端模型……

这是**思考过程**，也就是 D3 里那个 `TextReasoningContent` 分支处理的内容。

**在本地 qwen3 上一次都没命中过**，当时的判断是「Ollama 的 OpenAI 兼容层不回传思考增量」。
现在证明了：**代码是对的，只是本地 provider 不给，DeepSeek 给。**

### 要修正 D3 的一个结论

D3 笔记写的是「**流式压不掉思考时间**」。这句话需要加前提：

> 流式压不掉思考时间 —— **前提是 provider 不回传思考增量。**
> 如果回传（DeepSeek 就是），522 毫秒就有反馈，思考期不再是一片空白。

结论不变，适用范围变了。**不加这个前提，以后换 provider 会误判。**

### 顺带：幻觉这次更严重

非流式那次的回答是：

> 我是由 **OpenAI 开发的 ChatGPT**，是运行在云端的 AI 助手

**它说自己是竞品。** 间隔几秒的流式那次答的是「我是运行在云端的 AI 助手」，没提 OpenAI。

同一个问题、同一个模型、两次答案不同，而且差到了认错公司。

根因还是那个：**没有 System Prompt。** 模型不知道自己是谁，只能从训练数据里挑一个最眼熟的自我认知模板。
