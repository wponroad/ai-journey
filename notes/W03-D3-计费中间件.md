# W03-D3　Token 计费中间件

> 2026-11-18　目标：从「这一次花了多少」升级到「谁花的、哪个部门、累计多少」，并落库
> 一句话结论：**记账的价值不在数字本身，在于"失败也留痕"。只记成功的那几次，等于没记。**

## 一、今天的层次跃迁

| 层 | 问题 | 之前的实现 | 今天 |
|---|---|---|---|
| 单次 | 这一次多少钱 | `CostCalculator` + `LlmReply.Amount` | 不动 |
| **聚合** | **这个用户/部门累计多少** | 没有 | **`UsageStore` + SQLite** |

单次成本是**同步算出来的一个数**；聚合成本是**跨请求、跨进程、要能查询的一堆行**。

前者是计算，后者是存储。**一旦涉及存储，问题就全变了**：类型怎么存、并发怎么写、查不出来怎么办。

## 二、记账放在哪一层：两个方案

第一版我写了个 `MeteredLlmService` 装饰器，包在 `LlmService` 外面。被否掉了，理由成立：**`ILLMService` 有 5 个方法，5 段样板转发，代码复用度太低。**

改成直接注入：

```csharp
public LlmService(IChatClient chatClient, CostCalculator? cost = null,
                  UsageStore? usageStore = null,
                  string userId = "anonymous", string department = "unknown")
```

### 两种方案的真实差别

| | 装饰器（外层） | 注入（内部） |
|---|---|---|
| 代码量 | 5 个方法各写一遍 try/catch/转发 | 在已有出口加一行 |
| 能看到的范围 | 只有「一次逻辑请求」的最终结果 | 能看到工具循环各轮的累加 |
| 与治理逻辑的耦合 | 解耦 | 耦合 |
| 关掉记账 | 不包就行 | `store = null` |

### 一处必须承认的错误

我在推行装饰器时说「注入能看到重试花了多少」——**这句是错的**。

`UsageAccumulator` 记的是**工具循环每一轮**的用量（第 1 轮 513 + 第 2 轮 580 = 1093）。但 **pipeline 内部的重试**（超时后重试一次）它同样看不到——那层的消耗压根没变成一个 `response` 返回出来。

准确的说法：

| 能看见 | 看不见 |
|---|---|
| 工具循环各轮累加 | pipeline 内部失败的重试 |
| 降级前已经花掉的 | 每次 HTTP 调用的明细 |

**真正的两全其美要等 D5 的 OpenTelemetry**：span 天然嵌套，一次 trace 下面挂 N 个 span，既能聚合又能下钻。

## 三、`bool` 还是对象：一个值得记的设计讨论

我最初传 `UsageStore` 实例，他建议改成传 `bool enableLog`，理由「不想让调用者知道怎么记日志」。

最终选了第三条路：**配置化**。

### 为什么 `bool` 不行

```csharp
// 如果这样写
if (enableUsageLog) _usageStore = new UsageStore("data/usage.db");
```

**路径被写死进服务层了。** 这正是 W1 D5 定过的原则：「价格从外面递进来，服务自己不读配置」——数据库路径同理，不该由服务决定。

还有两个问题：

| 问题 | 后果 |
|---|---|
| 多实例各建一个 | SQLite 单文件写有锁，并发会 `database is locked` |
| 没法测试 | 传 `bool` 只能连真库，传对象可以传假的或 null |

### 一个判断标准

> **传对象 ≠ 泄漏细节。**
> 传 `IChatClient` 不等于调用方要懂 HTTP 协议；传 `UsageStore` 也不等于要懂 SQL。

真正泄漏细节的是「传一个 bool 然后内部 new 一个具体实现」——那等于把「默认用 SQLite 存到 data/ 目录」这个业务决策固化进了服务。

### 最终方案

```json
"Usage": {
  "Enabled": true,
  "DbPath": "data/usage.db",
  "UserId": "zhangsan",
  "Department": "技术部"
}
```

```csharp
var usage = config.GetSection("Usage").Get<UsageOptions>() ?? new UsageOptions();

var dbPath = Path.IsPathRooted(usage.DbPath)
    ? usage.DbPath
    : Path.Combine(AppContext.BaseDirectory, usage.DbPath);

var store = usage.Enabled ? new UsageStore(dbPath) : null;
ILLMService llm = new LlmService(chat, cost, store, usage.UserId, usage.Department);
```

三点都满足：调用方不知道「怎么记」、开关能关、路径可配。

**路径用 `AppContext.BaseDirectory` 解析**，而不是工作目录——否则 `dotnet run`（工作目录=项目目录）和 VS 调试（工作目录=bin）会写到两个不同地方。

## 四、SQLite 三个坑

### 坑一：没有 `decimal` 类型

SQLite 只有 `INTEGER` / `REAL` / `TEXT` / `BLOB`。

| 存法 | 问题 |
|---|---|
| `REAL`（浮点） | 累加出现浮点误差，一个月下来对不上账 |
| `TEXT` | 没法 `SUM` |
| **`INTEGER` 微元** | ✅ |

```csharp
// 0.000854 元 → 854 微元
public static long? ToMicros(decimal? yuan)
    => yuan is null ? null : (long)Math.Round(yuan.Value * 1_000_000m, MidpointRounding.AwayFromZero);
```

查询时 `/ 1000000.0` 还原。

**这是 W1「金额用 decimal 不用 float」那条原则的延伸——数据库那一层也得守住。**

### 坑二：可空列读出来必须判 `IsDBNull`

降级那行 `InputTokens` 是 NULL，`GetInt64(3)` 直接抛：

```
The data is NULL at ordinal 3. This method can't be called on NULL values.
```

**`GetInt64` 读到 NULL 不返回 0，而是抛异常。** 所以每一列都要判：

```csharp
var inTok = reader.IsDBNull(3) ? "—" : reader.GetInt64(3).ToString();
```

写的时候用 `(object?)null ?? DBNull.Value`，读的时候就要对应地判——**很容易只做一半**。

> 好在这个崩得响。**如果它静默返回 0，你会以为「降级那次花了 0 个 token」，而不是「没数据」。**

### 坑三：连接与并发

`Microsoft.Data.Sqlite` 内置连接池，所以 `new SqliteConnection` + `Open/Close` 不会真的每次开文件。

**但 SQLite 是单写者模型**：同一时刻只能有一个写事务。高频写入会出现 `database is locked`。

现在单线程无所谓，项目①的多租户场景要考虑：
- 写入串行化（队列）
- 或者换真正的数据库

## 五、四个记账位置

`LlmService` 里有四个出口，每个都要记：

| 位置 | Status | 说明 |
|---|---|---|
| `AskAsync` 成功 | `ok` | |
| `AskAsync` 抛异常 | `error` | 记完照样 `throw` |
| `AskWithToolsAsync` 成功 | `ok` | |
| `AskWithToolsAsync` 降级 | `fallback` | 带已消耗的 token |
| `AskWithToolsAsync` 其它异常 | `error` | 不在 `IsServiceDown` 清单里的 |
| `AskStreamAsync` 收到收尾片 | `ok` | `finally` 里记 |
| `AskStreamAsync` 中途断 | `error` + `StreamInterrupted` | |

**一句原则：记账是旁观者，不是替代者。** `catch` 里记完必须 `throw`，否则所有错误都会变成「记账成功但用户没拿到答案」。

## 六、`fallback` 为什么必须单独一个状态

```csharp
reply.IsFallback ? "fallback" : "ok"
```

如果降级也记成 `ok`：

| 后果 | 具体 |
|---|---|
| 降级率看不见 | 模型挂了三个月，你的报表显示「成功率 100%」 |
| 成本统计失真 | 降级不花钱，混进正常样本会拉低平均成本 |
| 用户投诉时无法回溯 | 查不出「那段时间其实是正则在答」 |

> **降级做得越好，故障越难被发现。** 所以降级必须显式留痕，而且要在界面、日志、数据库三个地方都留。

## 七、流式记账的硬约束

**C# 不允许在带 `catch` 的 `try` 里 `yield return`。** 所以流式只能用 `try/finally`：

```csharp
bool finished = false;
try
{
    await foreach (var chunk in ...) { yield return chunk; }
    yield return finalChunk;
    finished = true;
}
finally
{
    // finished = 走到最后一片；否则 = 抛异常，或调用方提前 Dispose
}
```

副作用：**拿不到异常类型**，只能标 `StreamInterrupted`。

要拿到异常就得手动枚举（`GetAsyncEnumerator` + `MoveNextAsync`），代码会复杂一倍。**现阶段不值得，记下来。**

## 八、记账位置决定账单精度

刚才那次请求，实测：

- 22:50 那次：`in 1093 / out 66`，耗时 11.3 秒
- 日志里先出现 `[retry 1] timeout 10s`，说明**实际调用了两次**
- 账上只有 **1 行**

**装饰器/注入层只能记「一次逻辑请求」，记不到「内部重试了几次」。**

真实 APM 系统是两层：

| 概念 | 记什么 | 粒度 |
|---|---|---|
| Transaction | 用户、部门、业务结果 | 一次请求 |
| Span | 每次 HTTP 调用 | 一次调用 |

**两个都要，粒度不同，不是重复。**

想在这一层解决，唯一可靠的办法是**把记账下沉到 `IChatClient`**——但那又拿不到用户和部门。**D5 的 OpenTelemetry 才是标准答案。**

## 九、实测数据

### 正常一次（`failTimes = 0`）

```
技术部：1 次 | 0.000854 元 | 成功 1 / 降级 0 / 失败 0
2026-11-18 22:50:08 | zhangsan | ok | in 1093 out 66 | 0.000854 元 | 11332ms
```

### 降级一次（`failTimes = 99`）

```
技术部：2 次 | 0.000854 元 | 成功 1 / 降级 1 / 失败 0
2026-11-18 22:56:46 | zhangsan | fallback | in — out — | —        | 6350ms
2026-11-18 22:50:08 | zhangsan | ok       | in 1093 out 66 | 0.000854 元 | 11332ms
```

**降级那行 `in — out —` 是对的**：熔断短路，请求压根没发出去，一个 token 都没消耗。

而 6350ms 是 4 次 429 + 退避的总耗时——**这 6 秒纯浪费**（模型根本没被调用）。正好说明熔断的价值：再往后问，这 6 秒也会消失。

### 一个没解释清楚的数字

同样 `in 1093 / out 66`，两次成本不同：

| 时间 | 成本 |
|---|---|
| 22:23 | 0.000353 元 |
| 22:37 | 0.000854 元 |

差 2.4 倍。两次都在空闲时段（0.5 折），单价相同，**唯一能解释的是缓存命中数不同**。

但顺序反了——后跑的那次反而更贵，按道理缓存应该更热。**原因待查，D4 做 Redis 缓存时会正面遇到。**

## 待补（自己写）

> 你把记账当「系统日志」来设计，这个类比挺准。但它们有一个关键区别：
>
> 日志丢了，最多是"查不到当时发生了什么"；**账单丢了，是真金白银对不上**。
>
> 你觉得这个区别，会怎么影响你对这张表的设计？（提示：日志可以异步、可以丢、可以采样；账单能吗？）
