## 二、这次实验有两处不能直接比，记下来免得以后误读

**① 组 A 内部，非流式 12634 ms 比流式的 TTFT 16928 ms 还小。**

看起来像「流式更慢」，其实是**两次独立请求，模型思考的长度不同**：非流式那次输出 165 token，  
流式那次输出 285 token。思考更久，第一片自然来得更晚。

**能比的是同一次请求内部**：TTFT 16928 对总耗时 19788 —— 首字来得早，后面还要等 2.8 秒才收尾。

**跨组比较必须控制变量**：只有组 A 和组 B 才构成有效对照，因为它们唯一的差别是思考开/关。

**② 同一个问句，两次输出 165 token 和 285 token，差 73%。**

这就是 W0 第 1 题里说的「同样的输入，返回可能不同」，今天在自己机器上被量化了。  
**连带后果：单次耗时不能当作性能基准**，要测响应速度必须多次取样取分布。

## 三、SSE：流式在传输层是什么

服务端做的事很朴素：**一个普通 HTTP 请求，响应体不关闭，持续往里写。**

```
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"choices":[{"delta":{"content":"我"}}]}

data: {"choices":[{"delta":{"content":"是"}}]}

data: [DONE]
```

- 每段以 `data: ` 开头，空行分隔
- **不是 WebSocket，不需要协议升级**，就是一个不提前关掉的响应
- 真正麻烦的地方在部署：反向代理默认会缓冲响应，必须关掉（Nginx 的 `proxy_buffering off`、  
  响应头 `X-Accel-Buffering: no`）。项目①进容器时会撞上

## 四、`IAsyncEnumerable`：流式在 C# 里的形态

```csharp
IAsyncEnumerable<ChatResponseUpdate> GetStreamingResponseAsync(...)
```

消费方式是 `await foreach`，不是 `foreach`。对应关系：

| 同步               | 异步                    |
| ---------------- | --------------------- |
| `IEnumerable<T>` | `IAsyncEnumerable<T>` |
| `MoveNext()`     | `MoveNextAsync()`     |
| 取值在内存里，立刻有       | 每次取值可能要等网络            |

**反面教材（等于没流式）：**

```csharp
var list = new List<LlmChunk>();
await foreach (var u in ...) list.Add(...);
return list;      // 全部到齐才返回，调用方还是干等
```

流式的前提是「算出一段就立刻交出去」，容器换了但返回时机没变，流式就是假的。

## 五、`yield return`：实现「交出去就暂停」

```csharp
yield return 一片;   // 交出这一片，方法暂停在这里，下次从这行继续
return;             // 结束整个方法
```

三个反直觉的性质：

1. **调用方法时方法体一行都不执行**。`llm.AskStreamAsync(q)` 返回的是「待执行的序列」，  
   真正开始跑是 `await foreach` 第一次 `MoveNextAsync()`。所以方法里的 `throw` 会在遍历时才爆，  
   异常出现在循环体，不在调用处
2. **局部变量跨 `yield` 保留**。这是 `input` / `output` 能声明在循环外、在循环里赋值、  
   循环外还能用的原因 —— 编译器把它们变成了状态机的字段
3. **`yield` 方法里不能用 `ref` / `out` 参数**，引用没法跟着状态机移动

`async/await` 和 `yield` 用的是同一套状态机机制（`<>1__state`），一个管异步等待，一个管迭代产出。

三条硬规则：返回类型必须是 `IEnumerable<T>` / `IAsyncEnumerable<T>`；不能出现 `return 值;`  
（只能 `yield break;`）；不能在 `try-catch` 的 catch 块里 `yield return`。

`[EnumeratorCancellation]` 这个特性存在的理由也在这里：`yield` 方法可能跨越几十秒、  
几百次暂停，调用方中途取消时，得让这个「睡着的方法」知道。

## 六、`ChatResponseUpdate` 里装的不止是文字

每一片 `ChatResponseUpdate` 身上有个 `Contents`，类型是 `IList<AIContent>` —— **是个列表**。  
因为一个 SSE 包可能同时塞好几样东西（正文最后一个字 + 本次用量）。

`AIContent` 是抽象基类，真正流过来的是子类：

| 子类                     | 内容       | 怎么处理                  |
| ---------------------- | -------- | --------------------- |
| `TextContent`          | 正文       | `yield return`，给用户看   |
| `TextReasoningContent` | 思考过程     | `yield return`，但要单独标记 |
| `UsageContent`         | token 用量 | **不 yield**，只记到局部变量   |
| `FunctionCallContent`  | 工具调用     | 现在没处理（见遗留）            |

分发靠 C# 的模式匹配 `switch`：

```csharp
switch (content)
{
    case TextContent text when !string.IsNullOrEmpty(text.Text):
        yield return new LlmChunk { Text = text.Text };
        break;
}
```

`case 类型 变量名` 一步做了两件事：**判断运行时类型，成功则拿到强类型引用**。  
等价于 `if (content is TextContent text && ...)`。`when` 是第二个条件，用来过滤空片  
（流式底下夹着大量文本为空的 update）。

**为什么不能直接用 `update.Text`**：那是便捷属性，只拼 `TextContent`，  
思考内容和用量都不在里面。第一版按这个写，思考内容全丢了。

**一个编译期才知道的事实**：`ChatResponseUpdate` **没有** `Usage` 属性。  
流式下用量也是当成一片 content 塞进来的。按非流式的直觉写会直接编译报错。

## 七、今天最值钱的发现：流式压不掉思考时间

组 A 里 TTFT 占了总耗时的 86% —— **流式几乎没改善首字延迟**。

原因：`qwen3:8b` 默认开思考，这 16 秒它在推理，**但推理过程没有作为流式片段发出来**。  
代码里专门写了 `TextReasoningContent` 分支来接思考内容，一次都没命中  
（`firstAnswer == ttft` 就是证据）。是 Ollama 的 OpenAI 兼容层不回传思考增量，不是接错了。

所以准确的结论是：

> **流式压缩的是「等待感」，压不掉「思考时间」。**

思考阶段是静默的，屏幕上什么都没有，流式改变不了这一点。这直接推出线上产品的三种做法：

| 做法                         | 代价               |
| -------------------------- | ---------------- |
| 关掉思考（`/no_think`）          | 回答质量下降           |
| 思考时显示「正在思考…」               | 用户还在等，但至少知道系统活着  |
| 换会回传思考内容的模型（如 DeepSeek R1） | 能看到推理过程，token 更贵 |

**这就是为什么大多数 AI 产品在思考时都有转圈或「Thinking…」字样** —— 不是装饰，是在填这段静默。

### 怎么关掉思考（具体做法）

在问题前面加 `/no_think` 四个字，写在 prompt 文本里：

```csharp
var question = "/no_think 用一句话介绍你自己。";
// 对比用，测完记得改回来
```

**这不是参数，是模型自带的指令：**

| | 传参（如 temperature） | `/no_think` |
|---|---|---|
| 写在哪 | `ChatOptions` 字段 | prompt 文本里 |
| 谁处理 | 协议层 / 服务端 | **模型的 chat template** |
| 换模型 | 一般通用 | **立刻失效** |

`/no_think` 是 Qwen3 训练时注入的约定，Ollama 加载模型时按 chat template 解析。
换到 DeepSeek、gpt 上它就是一句普通文本，毫无作用。

**为什么不能用参数传**：Ollama 原生 API（`/api/chat`）支持 `"think": false`，
但项目走的是 OpenAI 兼容层（`/v1/chat/completions`），协议里没有这个字段。
写进 `ChatOptions` 会被忽略，**不报错也不生效** —— 又是一次静默失败。

### 各家关思考的方式都不一样

| 模型 | 关闭方式 |
|---|---|
| qwen3 | prompt 开头加 `/no_think` |
| DeepSeek | **换模型名**：`deepseek-chat`（不思考）/ `deepseek-reasoner`（思考） |
| gpt-5 系列 | 用 `reasoning_effort` 调强度，不能完全关 |

同一个 `IChatClient`，每家的开关长得都不一样 —— 能力差异藏在模型自身，不在接口层。

## 八、结论

1. **SSE 不是 WebSocket**，就是「响应不关掉，一直往里写」，麻烦在反向代理的缓冲配置
2. **`IAsyncEnumerable` + `yield return` 是「来一片交一片」的语法基础**，  
   换成 `List` 就退化成假流式
3. **流式的收益要用 TTFT 衡量，不是总耗时**。总耗时一点没省
4. **TTFT 的上限由「第一个 token 什么时候产生」决定**，模型在思考的那段时间，  
   任何流式技术都插不进去
