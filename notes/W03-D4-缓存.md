# W03-D4　Redis 精确缓存 + 语义缓存

> 2026-11-19　目标：同一个问题问第二遍，不花钱
> 一句话结论：**缓存的前提是「同样的输入 → 同样的输出」。但 LLM 的输入不只是问题，还有时间、数据状态、用户身份 —— 只看问题就会缓存出错误答案。**

## 一、这件事你已经做过

本质就是接口缓存：**查之前先看缓存，有就返回，没有才查真源。**

| | 普通接口缓存 | LLM 缓存 |
|---|---|---|
| key | 用户 ID + 商品 ID（固定参数） | **一句自然语言** |
| 命中条件 | key 完全相等 | 一字不差，**或意思接近** |
| 难点 | 没有 | 「意思接近」可能把不同问题当成同一个 |

唯一的难点在最后一行，其余全是熟悉的套路。

## 二、三级决策路径

```
用户提问
  ├─ ① 精确缓存命中？        → 返回   2 ms    0 元
  ├─ ② 实体相同 且 相似度≥0.93 → 返回  28 ms    0 元
  └─ ③ 都没有 → 调模型 → 写回缓存      12891 ms  0.0017 元
```

三级之间差 **6000 倍耗时**、**100% 成本**。

为什么需要 ① 和 ② 两级：① 是 O(1) 的 KV 查询，② 要做 embedding + 遍历算余弦。**能用 ① 解决的不要走到 ②。**

## 三、为什么需要 embedding

精确缓存要求问题一字不差。但人不会重复自己的措辞：

```
"订单 A20261109 什么状态"
"订单 A20261109 状态如何"
"帮我看看 A20261109 这单"
```

三句话一个意思，精确缓存全 miss。

embedding 模型（`bge-m3`）把每句话变成一个 **1024 维浮点数组**，意思相近的句子向量也相近。于是"像不像"变成了一道几何题：算两个向量的余弦。

**它和聊天模型是同一种底层技术，两种用途**：聊天模型接"下一个 token 的概率"，embedding 模型接"整句压成一个点"。

## 四、实测：阈值靠不住（今天最重要的数据）

写代码之前先量了一下，bge-m3，1024 维：

| 句对 | 相似度 |
|---|---|
| 同义改写（…109 状态 / …109 状态如何） | **0.9543** |
| 语义相近（…109 状态 / 我最近那单怎么样） | 0.6523 |
| 完全无关（…109 状态 / 今天天气怎么样） | **0.4976** |
| **只差一个数字（…109 / …110）** | **0.9892** |
| 只差一个编号（SKU-001 / SKU-003） | 0.9283 |
| 间接相关 | 0.6451 |

### 三个反直觉的地方

**① 最该拦住的分数最高**

```
实体替换 0.9892   ← 想排除的
同义改写 0.9543   ← 想要的
```

**顺序是反的。** 阈值设 0.96：改写过不了，实体替换照命中。一个都拦不住想拦的。

**② 无关句子的基线是 0.5，不是 0**

`0.4976` —— 任意两句中文都有这个分数。所以"阈值 0.8"听起来严格，实际会放进来一大片无关内容。

**③ 我事先的预估全错，而且方向一致**

| 我猜 | 实际 | 偏差 |
|---|---|---|
| 同义 ~0.98 | 0.9543 | 略低 |
| 相近 ~0.75 | 0.6523 | 低 13% |
| 无关 ~0.2 | 0.4976 | **高 150%** |

**低估基线、高估区分度。** 说明对 embedding 的"感觉"完全不可靠，只能实测。

> 这本身就是一条方法：**任何涉及数值阈值的判断，先量再定。**

## 五、实体守卫：不是减分，是排除

因为阈值切不开，真正的判据变成了两段式：

```csharp
// 1. 先比实体
if (!SameEntities(queryEntities, cachedEntities)) continue;

// 2. 实体一致才允许参与相似度竞争
var score = Cosine(queryVec, vec);
```

**注意是 `continue`，不是"扣分"。**

- 扣分：它还在候选里，可能被别的因素挤上来
- `continue`：它根本没资格参与

### 用你熟悉的场景理解

做过租户系统的都知道这条铁律：

> **缓存 key 里必须带租户 ID，否则 A 公司的数据会返回给 B 公司。**

后果和今天这个一模一样：

| | 少了什么 | 后果 |
|---|---|---|
| 多租户缓存 | key 里没租户 ID | A 的数据给了 B |
| 语义缓存 | key 里没订单号 | A 的订单金额给了 B |

**同一个错误，换了层皮。** 所以那行 `continue` 不是优化，是**正确性底线**。

### 实测结果

```
订单 …109 什么状态  → 未命中，调模型 → "已发货，128.50 元"
订单 …109 状态如何  → 语义命中 0.9525 → 同上
订单 …110 什么状态  → 未命中（相似度 0.99 但实体不同）→ "待付款，99.00 元" ✓
```

**第 4 条是今天真正的成果**：如果只靠阈值，这里必然返回 128.50 元。

## 六、第二个坑：有些问题根本不能缓存

这是他自己提出来的，比技术细节重要：

> 昨天问「今天最大的一笔订单是多少钱」，今天问一模一样的话，**两次的正确答案不同。**

一字不差，但缓存 24 小时就是 24 小时的错误答案。

### 缓存的前提被破坏了

```
答案 = f(问题, 当前时间, 数据库状态, 用户身份)
```

而 key 里只有 `问题`。**另外三个全丢了。**

### 判断标准：缓存「知识」，不缓存「计算结果」

| 问题类型 | 能缓存吗 | 例子 |
|---|---|---|
| 静态知识 | ✅ | “退货政策是什么”、“Redis 和 Memcached 区别” |
| 业务规则 | ✅ | “发票怎么开”、“多少免运费” |
| **相对时间** | ❌ | “今天/最近/上周 最大的一笔” |
| **聚合统计** | ❌ | “一共多少”、“排名前 10”、“合计” |
| **实时状态** | ❌ | “订单到哪了”、“还有多少库存” |
| **用户相关** | ❌ | “我的订单”、“我是谁” |

> 知识类问题的答案是**固定的**；数据类问题的答案是**算出来的**。
> **算出来的东西不能缓存，因为基表随时在变。**

### 三道闸

**① 准入判断（黑名单）**

```csharp
public static bool IsCacheable(string question, out string reason)
{
    var time = Regex.Match(question, @"今天|昨天|最近|现在|本月|上周|今年");
    if (time.Success) { reason = $"含相对时间「{time.Value}」"; return false; }

    var agg = Regex.Match(question, @"最大|最小|最多|最少|一共|总共|合计|排名|平均");
    if (agg.Success) { reason = $"含聚合统计「{agg.Value}」"; return false; }

    reason = "";
    return true;
}
```

**查询和写入都要拦** —— 只拦查询的话，第一次照样会写进去，第二次就被查出来了。

**② TTL 分级**

| 内容 | TTL |
|---|---|
| 静态知识 | 几小时 ~ 几天 |
| 业务规则 | 1 ~ 24 小时 |
| 半实时 | **5 ~ 30 分钟** |
| 实时数据 | **0，不缓存** |

TTL 是「我最多能容忍多久的过期答案」——**给自己留的止损线**。

**③ 时间归一化**（没做）

如果非要缓存带时间的问题，把"今天"解析成 `2026-11-19` 塞进 key：

```
今天最大的一笔 → key 带 2026-11-19
明天同样的话   → key 是 2026-11-20 → 自动不命中
```

但仍然拦不住"同一天内数据变了"，所以 TTL 还是要短。

### 实测：闸门生效

```
① 最近那单什么状态 → [cache] 跳过：含相对时间「最近」 → 调模型
② 最近那单什么状态 → [cache] 跳过                    → 又调了一次模型
```

**两次答案措辞不同**（"最近那单（订单号 …）的状态是已完成" vs "最近的订单号是 …，状态为已完成"），这就是"真的没走缓存"的反向证据——**如果命中，两次应该一字不差**。

## 七、三个工程细节

### ① `ConnectionMultiplexer` 必须是单例

```csharp
_redis = ConnectionMultiplexer.Connect(conn);   // 整个进程一个
```

它内部维护连接池、订阅、心跳。每次 `new` 一个会瞬间打爆服务端连接数。**这是 Redis 客户端最经典的使用错误。**

### ② 向量存二进制，不存 JSON

```csharp
float[] → byte[]  = 1024 × 4 = 4 KB
JSON 字符串       ≈ 12 KB
```

三倍差距，而且反序列化快得多。

### ③ 命中率的分母

```csharp
int eligible = total - _skipped;              // 只算「本来可以缓存」的
double rate = (exactHit + semanticHit) / eligible;
```

如果把"按规则不缓存"的也算进分母：

```
3 次查询，2 次不可缓存，1 次命中 → 33%（看起来缓存没用）
3 次查询，分母取 1              → 100%（真实情况）
```

**分母错了，结论就反了。**

## 八、实测数据

环境：Memurai 8.2.0（Redis 8.2.10 兼容）+ bge-m3（1024 维）+ qwen3:8b

| 路径 | 耗时 | 成本 |
|---|---|---|
| 未命中（调模型） | 12891 ms | 0.001709 元 |
| 精确命中 | **2 ms** | 0 |
| 语义命中 | **28 ms** | 0 |

`28 - 2 = 26 ms` 是"embedding + Redis 查询 + 14 次余弦（1024 维）"的全部开销。

**说明小数据量下自己算余弦完全够用**，不用一上来就上向量数据库。几千条以后才需要换 RediSearch / pgvector。

## 九、一个反直觉的结论

真实业务系统里，用户问得最多的是「最近那单」「库存还有多少」——**全是实时查询，全都不能缓存**。

> **缓存能省的钱，比你预期的少。**
> 它只对「知识类」问题有效，而业务系统里大量是实时查询，**这部分成本是刚性的**。

那这类成本怎么降？三条路，都不是缓存：

1. **让工具更便宜**：`GetLatestOrderNo → GetOrder` 两步能合并成一步
2. **让模型更小**：查询型任务不需要 8B
3. **产品层面减少重复提问**：常见问题做成按钮/菜单

**这三条比缓存更接近真实优化路径。**
