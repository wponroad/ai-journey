# W03-D6　单元测试

> 2026-11-21　目标：重试与降级路径能被自动验证；人为制造 429 证明不雪崩
> 一句话结论：**有些事实只有假对象能证明 —— 比如"调用了 3 次"和"一次都没调用"。**

## 一、为什么手动跑过了还要写测试

| | 手动跑一次 | 单元测试 |
|---|---|---|
| 耗时 | 12 秒 | **247 毫秒（全部 12 个）** |
| 成本 | 0.0017 元 | **0** |
| 依赖 | Ollama + Redis 都得活着 | **不依赖** |
| 结果 | 模型输出会变，没法断言 | **确定** |
| **验证失败路径** | **做不到** | **可以精确编排** |
| 改代码后回归 | 重跑几轮对话 | **3 秒** |

最后两条是关键：

**「验证失败路径」做不到** —— 你没法让真实服务"第 2 次调用精确失败"。拔网线是全失败，等它偶尔 429 是碰运气。

**「回归」是日常收益** —— 以后改 `LlmService` 一行，247 毫秒就知道有没有破坏重试/降级/熔断。

## 二、`FakeChatClient`：不是假数据，是剧本播放器

```csharp
var fake = new FakeChatClient([E429(), E429(), null], "已发货，128.50 元");
//                              ↑      ↑      ↑
//                            第1次  第2次  第3次
```

内部就是一个队列，每次调用出队一个：

```csharp
public Task<ChatResponse> GetResponseAsync(...)
{
    Interlocked.Increment(ref _callCount);

    if (_script.TryDequeue(out var ex) && ex is not null)
        return Task.FromException<ChatResponse>(ex);

    return Task.FromResult(new ChatResponse(...));
}
```

**剧本用完默认成功** —— 这是约定，测试里只写"要失败几次"。

它和你写过的 `Substitute.For<IOrderRepository>()` 是同一个东西，只是手写 20 行。

### 三个必须注意的实现细节

| 细节 | 为什么 |
|---|---|
| `Task.FromException` 而不是 `throw` | 非 async 方法里 `throw` 是同步抛出，两条失败路径行为不一致 |
| `GetService` 返回 `null`，**不能抛异常** | `LlmService.ToReply` 会调 `GetService<ChatClientMetadata>()`，抛异常让所有测试崩在那一行 |
| `CallCount` 必须暴露 | 后面所有"调了几次"的断言全靠它 |

## 三、三个核心断言

```csharp
// ① 一次成功
Assert.Equal(1, fake.CallCount);          // 没有多余调用

// ② 前两次 429，第三次成功
Assert.Equal(3, fake.CallCount);          // 恰好 1 次原始 + 2 次重试

// ③ 一直 429
Assert.True(reply.IsFallback);            // 降级兜住了，没抛异常给用户
```

**② 是核心**："恰好调了 3 次"这个事实，用真 client 永远断言不出来。

### 一处容易混的语义

`IsFallback` 不是"失败"的标记，是"**这次回答由规则生成，不是模型生成**"的标记。

| 情况 | `IsFallback` | 拿到答案了吗 |
|---|---|---|
| 3 次重试后成功 | `false` | ✅ 模型给的 |
| 重试用完，规则兜底 | **`true`** | ✅ 正则查的 |
| 真正失败 | — | ❌ 抛异常 |

**所以 `IsFallback == true` 是"降级成功"，不是"失败"。** 写断言时写反过一次，就是因为这个名字容易被读成"出问题了"。

## 四、熔断：用"没有发生"来断言

```csharp
// 第 1 次请求：重试用完，熔断打开
await llm.AskWithToolsAsync(...);
var afterFirst = fake.CallCount;

// 第 2 次请求：熔断已打开
await llm.AskWithToolsAsync(...);
var afterSecond = fake.CallCount;

Assert.Equal(afterFirst, afterSecond);     // 一次都没调
```

**"没有发生"是没法用真 client 断言的。** 真 client 你只能说"耗时很短，应该没发请求"——那是猜。用 fake，`CallCount` 没涨就是真的没发。

### 为什么能断言"不重试"

熔断打开后抛 `BrokenCircuitException`，这个异常**不在 `Retry` 的 `ShouldHandle` 清单里**，所以重试不会重试它，直接冒出去。

**这个设计是对的**：熔断的意思是"别试了"，再重试它毫无意义。

## 五、缓存准入：纯函数测试最划算

```csharp
[Theory]
[InlineData("今天最大的一笔订单是多少", false, "相对时间")]
[InlineData("最近那单什么状态",        false, "相对时间")]
[InlineData("最大的一笔订单",          false, "聚合统计")]
[InlineData("一共有多少笔订单",        false, "聚合统计")]
[InlineData("订单 A20261109 什么状态", true,  "")]
[InlineData("退货政策是什么",          true,  "")]
public void 缓存准入判断(string question, bool expected, string reasonKeyword)
```

**`IsCacheable` 是 `static` 纯函数**：不依赖网络、不依赖时间、不依赖任何外部状态。

> **一天里最划算的测试就是这种**：零成本、零抖动、跑一万遍结果一样。
> 写代码时优先把逻辑抽成纯函数，测试成本会低一个数量级。

`[Theory]` + `[InlineData]` 让 6 个用例写成 6 行数据，而不是 6 个方法。

## 六、并发雪崩：100 → 4

这是 W3 门槛的原话「人为制造 429 验证不雪崩」的直接证据。

```csharp
// 20 个请求同时打进来，全部遇到 429
var tasks = Enumerable.Range(0, 20)
    .Select(i => llm.AskWithToolsAsync(Ask($"订单 A202611{i:00} 什么状态")))
    .ToList();

await Task.WhenAll(tasks);

Assert.InRange(fake.CallCount, 4, 10);
```

实测结果：

| | 真实调用次数 |
|---|---|
| 假设没有熔断（20 × 5 次尝试） | **100** |
| 实际（熔断打开后短路） | **4** |

**省掉 96%。**

前 4 次失败达到 `MinimumThroughput = 4` 且失败率 100% → 熔断打开 → 剩下 16 个请求一次都没发出去。

### 断言写法上的一个取舍

```csharp
Assert.InRange(fake.CallCount, 4, 10);   // ✅
Assert.True(fake.CallCount < 20);        // ⚠️ 太松，19 次也过
Assert.Equal(4, fake.CallCount);         // ⚠️ 太脆，改阈值就红
```

**先跑一次读出真实值（4），再定范围。** 写断言之前不要猜。

## 七、两个让测试"活得下去"的改动

### ① 重试延迟可注入：10 秒 → 226 毫秒

原来 pipeline 建在字段初始化里，`Delay = TimeSpan.FromSeconds(1)` 写死：

```csharp
// 改前：测试要真的等 1s + 2s + 4s
private readonly ResiliencePipeline _pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions { Delay = TimeSpan.FromSeconds(1), ... })
```

改成构造函数里建，延迟可传：

```csharp
public LlmService(..., TimeSpan? retryDelay = null)
{
    _pipeline = new ResiliencePipelineBuilder()
        .AddRetry(new RetryStrategyOptions
        {
            Delay = retryDelay ?? TimeSpan.FromSeconds(1),   // 生产 1s，测试 10ms
            ...
        })
        .Build();
}
```

**结果：10 秒 → 226 毫秒，快 44 倍。**

> **这不是测试技巧，是设计原则：时间、随机数、时钟这类"环境变量"应该可注入。**
> 写死的时间参数 = 写死的测试时长 = 没人愿意跑测试。

### ② 断言范围而不是精确值

`Assert.Equal(4, ...)` 在参数微调后必然红，而代码其实没错。**测试应该锁"行为"，不锁"实现细节"。**

## 八、假对象自己也要并发安全

写并发测试时发现的：

```csharp
CallCount++;                          // 非原子，并发下丢计数
new Queue<Exception?>(script)         // 非线程安全，同时 Dequeue 抛异常
```

改成：

```csharp
Interlocked.Increment(ref _callCount);
new ConcurrentQueue<Exception?>(script);
```

**不改的后果**：你看到的 `CallCount` 比真实值小，"断言调了 4 次"可能是"其实调了 8 次但丢了 4 次计数"。

> **假对象有 bug，测出来的结论就是假的。** 而且它比被测代码的 bug 更难发现，因为你不觉得测试代码需要认真写。

## 九、测试的边界

| 验证什么 | 工具 |
|---|---|
| 重试几次、降级有没有触发、熔断打没打开、缓存该不该走 | **FakeChatClient** |
| 模型答得对不对、幻觉多不多 | 真模型 + 评测集（W2 的事） |

**测试是"控制变量"，不是"造假设定"。** 把模型固定成一个按剧本走的演员，才能看清自己的调度逻辑。
