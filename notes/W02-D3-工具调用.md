# W02 · Day 3　工具调用：模型只请求，执行在你这里

> 日期：2026-11-11（周三）　模型：qwen3:8b（本地 Ollama）　项目：HelloLlm
> 目标：定义三个工具，跑通完整的 tool-calling 循环。

---

## 一、核心分工：模型不执行任何代码

**模型只会输出一个「我想调用某个函数」的结构化请求。执行这件事永远在你的应用层。**

```
① 你问：SKU-003 还有货吗？十件多少钱？
② 模型返回的不是文字，是：GetStock("SKU-003")
③ 你的代码执行这个方法的真身 —— 模型碰不到
④ 把结果当成一条 Tool 消息塞回对话历史
⑤ 模型看到结果，决定：继续调下一个，还是给最终答案
⑥ 拿到最终回答，循环结束
```

**这个分工决定了安全边界**：哪些工具能被调用、能查什么数据、能操作什么资源，全部由你的代码决定。
**模型只能"申请"，不能"越权"。**

**循环的终止条件是「模型不再返回调用请求」** —— 它可能一轮就停，也可能连调三个工具。所以必须加最大步数保护。

## 二、三个工具

```csharp
[Description("按订单号查询订单详情，返回订单状态和金额。订单不存在时返回提示。")]
public string GetOrder([Description("订单号，例如 A20261109")] string orderNo)

[Description("按商品编号查询库存数量和单价")]
public string GetStock([Description("商品编号，例如 SKU-001")] string sku)

[Description("按商品编号和数量计算总价。数量超过库存时会返回库存不足。")]
public string CalcPrice([Description("商品编号")] string sku,
                        [Description("购买数量，必须是正整数")] int qty)
```

### 三个设计决定

**① `[Description]` 不是注释，是写给模型看的接口文档。**

模型看不到实现，只能看到描述和参数类型。**描述写得含糊，它就不知道什么时候该调、参数该填什么。**

**② 返回 `string` 而不是 `int` / `decimal`。**

最初的版本返回 `int GetStock()` 和 `decimal CalcPrice()`，但那样**没法表达错误**：

- 返回 `-1`：模型看到 -1，不知道怎么跟用户解释
- 抛异常：模型只能看到一句异常信息，可能不理解业务含义
- **返回字符串**：`"SKU-003 库存不足：当前只有 7 件，买不了 10 件"` —— 模型直接转述给用户

> **工具的返回值最终是给模型读的文本，不是给程序用的数据。**
> 类型简洁不重要，"说得清楚"才重要。

**③ 每个失败分支都要写清原因，并且给可用的示例。**

`"查不到订单 A99999。现有示例订单号：A20261109、A20261110、A20261111。"`

加了后半句，模型能自己纠正、换一个再试，而不是直接告诉用户"查不到"。

### 一个技术细节：为什么要用委托

```csharp
Tools = [
    AIFunctionFactory.Create((GetOrderDelegate)_orderService.GetOrder),
    AIFunctionFactory.Create((GetStockDelegate)_orderService.GetStock),
    AIFunctionFactory.Create((CalcPriceDelegate)_orderService.CalcPrice)
]
```

`AIFunctionFactory.Create` 需要从方法里推断出名称和参数。直接传方法组，在有重载时会歧义。

**显式转成自定义委托类型最稳**，`AIFunctionFactory` 能拿到明确的 `MethodInfo`。

委托类型定义放在工具方法同一个文件里（`OrderService.cs`），比藏在 `LlmService` 内部好找。

## 三、循环怎么跑起来

**只设置 `Tools = [...]` 是不够的。** 那只告诉模型"有哪些工具可用"，返回的仍是一条调用请求，`Text` 是空的。

需要跑循环。今天用 MEAI 的装饰器：

```csharp
_chatClient = new ChatClientBuilder(chatClient)
    .UseFunctionInvocation(c => c.MaximumIterationsPerRequest = 5)
    .Build();
```

它包在真实 client 外面，内部自动完成：拿调用请求 → 反射执行工具 → 结果塞回消息 → 再问一次 → 直到不再请求调用。

`MaximumIterationsPerRequest = 5` 是**死循环保护**：不设上限，一个写错的循环能烧掉一整天的额度。

**注意：`ChatClientBuilder` 和 `UseFunctionInvocation` 在 `Microsoft.Extensions.AI` 主包里**，
而 `Microsoft.Extensions.AI.OpenAI` 只依赖 `.Abstractions`，不会自动带上主包，要单独装。

## 四、实测结果

问：*"客户要买 SKU-003 十件，帮我看看有没有货、总共多少钱"* + *"订单 A20261109 什么状态"*

```
SKU-003 当前库存只有 7 件，单价 199.00 元，无法满足购买 10 件的需求。
订单 A20261109 的状态是已发货，金额为 128.50 元。

token 输入 1023 / 输出 156
```

**三个工具全部被调用，而且失败分支走通了。**

最关键的是第二行 —— 工具返回"库存不足，买不了 10 件"，**模型照实转述，没有编造一个"可以买"**。

> 这说明工具的错误信息写得够清楚：**你给模型什么样的话，它就还给用户什么样的话。**

## 五、今天的新发现：工具定义要占 token

看到 `输入 1023` 时以为是多轮累积，量了一下才发现大头在工具定义上。

**同一句话，只改带不带 tools：**

| | prompt token | 返回的 content |
|---|---|---|
| 不带 tools | **21** | 正常文字 |
| 带 1 个 tool | **157** | **空字符串** |

**差值 136 token —— 一个工具定义（名称 + 描述 + 参数 schema）的固定开销。**

按这个比例，三个工具约 **400 token**。总输入 1023 里，剩下的来自多轮累积（每次请求工具，前面的内容都要重发）。

### 两个直接结论

**① `content` 是空的，是「模型返回的不是文字」的直接证据。** 图上第②步的实证。

**② 工具不是免费的，它们是常驻的 prompt 开销。**

估算：400 token × 每天 10 万次 = 4000 万 token。按 DeepSeek 输入价 2 元/百万（空闲五折 1 元），
**光工具定义一天就是 40 元**。而这笔钱换来的是"模型知道有哪些工具可用"，不是任何实际业务结果。

### 实践上的平衡

| 工具描述 | 后果 |
|---|---|
| 太短（"查库存"） | 模型不知道何时该用，不调或者调错 |
| 太长（一段说明） | 每轮都付几十上百 token |
| 适中（一句用途 + 参数示例） | 现在这个长度是合适的 |

**真实项目里工具不会一上来挂几十个**，而是按场景分组：客服场景挂订单相关，库存场景挂库存相关。
**这也是"工具检索"这类方案存在的原因** —— 工具太多时，先让模型挑工具，再挂给模型。

## 六、结论

1. **模型只请求，不执行。** 执行权在你手里，这是安全边界
2. **`[Description]` 和参数类型就是工具的接口文档**，模型只看得到这些
3. **工具返回字符串，不是为了好看，是为了让错误也能被模型理解**
4. **只有 `Tools` 不跑循环，模型会一直请求调用而不给你答案**
5. **每个工具定义约 136 token，且每轮重发** —— 工具数量是成本的一部分
6. **失败分支要写得像人话**，模型会把你的话原样交给用户
