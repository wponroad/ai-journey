## 二、门槛自查

### ① 连续 10 次调用 0 解析失败

**远超要求**：5 轮 × 10 个用例 = **50 次调用，0 失败**。

用例覆盖了单工具、双工具并行、串行依赖、查不到、已售罄、超库存、模糊指代、不需要工具八种情况。

**边界**：这是 qwen3:8b + 这 10 个用例的成绩。换模型或换更难的输入，失败率会变。

### ② 能说出模型为什么「编造参数」以及怎么防

**为什么会编造**：模型没有真实数据，只能从训练分布里"猜一个合理的"。

三种触发场景：
1. **该调工具却没调**（觉得"这个问题我能答"）
2. **工具描述模糊**（不知道参数该填什么，猜一个）
3. **工具返回失败后**（不去追查原因，直接编一个结果）

**怎么防，四层：**

| 层 | 做法 |
|---|---|
| 工具设计 | 描述写清"什么时候用、参数是什么、返回什么"；职责不重叠 |
| prompt 约束 | 明确"需要真实数据必须调工具，不要凭印象回答" |
| 结果校验 | 解析失败 / 字段为空要能检测出来（D1 的假成功） |
| 循环保护 | 最大步数 + 失败降级，不让它无限重试 |

## 三、W2 三问

### Q1　结构化输出有哪几种实现路径？各有什么代价？

**四条路，保证程度递增，代价也递增：**

| 路径 | 保证什么 | 代价 |
|---|---|---|
| ① prompt 里写"请输出 JSON" | 什么都不保证 | 会带 markdown 包裹、多余解释、字段乱起名 |
| ② `response_format: json_object` | **合法 JSON** | 不保证字段名和类型 |
| ③ `response_format: json_schema` | **结构和字段** | provider 支持不一致（Ollama 支持，但不是所有家都支持） |
| ④ 工具调用（function calling） | 结构最稳 | 流程更绕，要跑循环 |

**本周实测数据：**

| prompt | 格式 | 结果 |
|---|---|---|
| 弱（只有"你是抽取器"） | `json_object` | ❌ 中文键名，0/5 可用 |
| 弱 | `json_schema` | ✅ 5/5 |
| 强（四段式） | `json_object` | ✅ 10/10 |
| 强 | `json_schema` | ✅ 10/10 |

> **结论：prompt 是主路，schema 是兜底。两者叠加最稳。**
> `json_object` 只保证"能 parse"，`json_schema` 才保证"字段对"。

**还有一个容易忽略的：`json_object` 模式下模型仍会用中文键名**（如果 prompt 是中文的），这时 `PropertyNameCaseInsensitive` 救不了——中文和英文不是大小写问题。

### Q2　模型调错了工具，工程上怎么处理？

**顺序很重要：先查工具设计，再查模型。**

**第一步：工具职责是否重叠？**

本周真实撞到的例子：

| 工具 | 返回什么 |
|---|---|
| `GetStock` | 库存数量 + 单价 |
| `CalcPrice` | 总价（内部也查了库存和单价） |

**两个工具都能给"库存/单价"信息，模型就要在两者之间挑——这是调错的根源。**

原则：**一件事只由一个工具回答。**

**第二步：工具描述是否足够区分？**

描述里要写清"什么时候用我"、"什么时候不该用我"。
`GetLatestOrderNo` 的描述如果不是"当用户说最近那单但没给订单号时，先用这个"，模型可能不会想到它。

**第三步：工具内部要返回可读的失败信息，不是错误码。**

```csharp
// 不好：模型不知道怎么解释
return -1;

// 好：模型能直接转述
return $"SKU-003 库存不足：当前只有 7 件，买不了 10 件";
```

**第四步：循环层兜底。**

- 最大步数保护（防止无限调用）
- 工具执行失败当成结果返回（`result = $"工具执行失败：{ex.Message}"`），不让异常打断整个对话
- 生产环境还应该有重试和降级

### Q3　Function Calling 和 MCP 是什么关系？

**互补，不是替代。**

| | Function Calling | MCP |
|---|---|---|
| 层面 | **模型侧**：模型输出"我想调用某个函数"的结构化请求 | **工程侧**：标准化"工具/数据源怎么暴露和被发现" |
| 解决什么 | 模型怎么表达"我要调什么" | 工具怎么被不同的 AI 应用复用 |
| 谁定的 | 各模型厂商（OpenAI 提出，各家跟进） | 开放协议（Anthropic 发起，多家支持） |

**官方对 MCP 的定位**：*"像 AI 应用的 USB-C 接口"* —— 标准化的连接方式。

**两者的关系**：一个 MCP Server 暴露出来的工具，**最终还是以 Function Calling 的形式被模型调用**。

> 打个比方：**Function Calling 是函数签名，MCP 是插件协议。**
> 前者让模型知道"有个函数叫什么、参数是什么"，后者让工具能"装上就能用"，不用为每个应用重写一遍。

**对项目的意义**：这周做的 `AIFunctionFactory.Create(...)` 是 Function Calling 的封装。如果将来要接第三方工具（比如查地图、发邮件），MCP 能省掉大量对接工作。
