## 一、为什么不继续用装饰器

昨天用 `UseFunctionInvocation()` 一行跑通了工具调用。今天把它拆掉自己写，理由三条：

1. **装饰器是黑盒**：不知道它调了几次、每次带了什么、什么时候停
2. **要看见成本**：只有自己写循环，才能打印每一步的 token
3. **网关必须手写**：项目①要在循环里插日志、计费、超时、熔断，装饰器给不了这些控制点

## 二、循环的五个关键点

```csharp
var chatMessages = ToChatMessages(messages);
var options = BuildOptions(settings);

for (int step = 1; step <= maxSteps; step++)
{
    var response = await _rawClient.GetResponseAsync(chatMessages, options);

    // ① assistant 消息必须回填历史
    chatMessages.AddRange(response.Messages);

    // ② 调用请求藏在 assistant 消息的 Contents 里
    var calls = response.Messages
        .SelectMany(m => m.Contents)
        .OfType<FunctionCallContent>()
        .ToList();

    if (calls.Count == 0) return ToReply(response, ...);   // ③ 没有请求 = 结束

    foreach (var call in calls)
    {
        var fn = _tools.OfType<AIFunction>().First(f => f.Name == call.Name);
        var result = await fn.InvokeAsync(new AIFunctionArguments(call.Arguments));  // ④ 执行

        chatMessages.Add(new ChatMessage(ChatRole.Tool,
            [new FunctionResultContent(call.CallId, result)]));   // ⑤ 绑定 CallId 回传
    }
}
throw new InvalidOperationException($"工具调用超过 {maxSteps} 步仍未结束");
```

**五个坑，逐个说：**

**① assistant 消息必须回填。** 它里面装着 `FunctionCallContent`，模型靠它记住「我刚才请求过什么」。不回填的话它会一直重复请求同一个工具。

**② `ChatResponse` 上没有 `Contents`。** 要穿过 `response.Messages` 才能拿到（第一版写 `response.Contents` 直接编译报错）。

**③ 终止条件是「没有调用请求」**，不是「拿到文字」。两个条件其实等价，但按前者判断更准确。

**④ 工具执行要按 `call.Name` 分发。** 这里从 `_tools` 里找同名的 `AIFunction` 调用。生产环境应该用字典而不是 `First()` 线性查找。

**⑤ `FunctionResultContent` 必须绑定 `call.CallId`。** 模型靠这个 ID 把结果和请求对上，绑错就是乱套。

**工具执行失败不能抛出去**——整个对话会断。正确做法是把错误也当成结果返回：

```csharp
catch (Exception ex) { result = $"工具执行失败：{ex.Message}"; }
```

模型看到"失败"，至少能告诉用户，而不是整个请求 500。

## 三、实测：串行 vs 并行

### 并行版

问题：*"SKU-001 我要买 5 件，总共多少钱？顺便查一下订单 A20261109 的状态。"*

```
[step 1] messages=3  输入=417 token  调用=CalcPrice, GetOrder
[step 2] messages=6  输入=550 token  调用=无（给最终回答）
```

**模型一轮请求了两个工具**（并行），所以只用 2 轮。

### 串行版

问题：*"我最近那单现在什么状态？"* ——**故意不给订单号**，必须先查号才能查详情。

```
[step 1] messages=3  输入=462 token  调用=GetLatestOrderNo
[step 2] messages=5  输入=502 token  调用=GetOrder
[step 3] messages=7  输入=568 token  调用=无（给最终回答）
```

**三步严格按顺序。** 没有第一步的返回值，第二步的参数根本填不出来。

### 对比

| | 轮数 | 每轮输入 | **总消耗** |
|---|---|---|---|
| 并行 | 2 | 417 / 550 | **967** |
| 串行 | 3 | 462 / 502 / 568 | **1532** |

**串行比并行多付 58%。** 原因是每多一轮，前面的全部内容（含工具定义）再付一次。

### 消息增长规律

| 场景 | 每轮 messages 增量 |
|---|---|
| 并行调 2 个工具 | **+3**（1 assistant + 2 Tool） |
| 串行调 1 个工具 | **+2**（1 assistant + 1 Tool） |

**调用次数越多，列表越长，每轮重发的就越多。这是个自我强化的成本。**

## 四、步数保护

把 `maxSteps` 改成 1 跑一次：

```
[step 1] messages=3 输入=417 token 调用=CalcPrice, GetOrder
Unhandled exception. System.InvalidOperationException: 工具调用超过 1 步仍未结束，可能陷入了循环。
```

**保护生效了，但代价要注意：**

- 那一刻 417 token **已经花掉**，两个工具**也执行了**，但结果被丢弃
- 上限不能设太小，否则每次都在白花钱
- 生产环境更合适的做法不是抛异常，而是**降级**：把已拿到的信息整理成「部分结果」返回

## 五、今天最重要的发现：合并提问会让模型「浅尝辄止」

同一个模型，同一个工具集，**换一种问法，行为完全不同**。

| 问法 | 步数 | token | 结果 |
|---|---|---|---|
| 单独问「最近那单怎么样」 | **3 步**（查号 → 查详情 → 回答） | 1532 | ✅ 完整 |
| 三个问题合并问 | **2 步**（一轮并行调 3 个工具 → 回答） | **1155** | ❌ 漏了最近订单的详情 |

**合并省了 25% 的钱，但答案残缺。**

### 为什么

1. **并行优先**：模型看到 3 个独立问题，第一反应是"能同时调的都调了"，一轮用完 3 次调用机会就直接收工
2. **它不觉得还需要第二步**：单独问时只有一条路径，它只能往下走；合并问时它觉得"三件事都办了"
3. **注意力被分散**：8B 模型对每件事的深挖意愿都降低了

> **这不是 bug，是 LLM 的行为特性：它倾向「完成度」，而不是「穷尽性」。**

### 工程含义

> **一个请求只做一件事，尤其是需要多步推理的事。**

| 做法 | 谁在控制 | 后果 |
|---|---|---|
| 一句话塞三个任务 | 模型自己决定做多深 | **不可控**，省钱但答案残缺 |
| 拆成三次请求 | 你的代码 | 每步结果可校验 |
| workflow 编排 | 代码决定顺序和依赖 | 模型只管单步 |

### 一个判断标准

> **用户这一句话，需要模型做几次「决策 → 调用 → 再决策」？**
>
> - 0 次（直接答）：随便合并
> - 1 次（调个工具就够）：可以合并
> - **≥2 次（有依赖、要追查）：必须拆开**

"最近那单怎么样"是 2 次决策（先查号、再查详情），**它不该和其他问题挤在一起。**

## 六、成本数据汇总（这周攒下的）

| 项目 | 数值 |
|---|---|
| 有参数的工具定义 | ~136 token |
| 无参数的工具定义 | ~45 token |
| 并行 2 轮（2 个工具） | 967 token |
| 串行 3 轮（各调 1 个） | 1532 token |
| 合并 3 问（并行 3 工具） | 1155 token |

**两个直接可用的结论：**

1. **工具定义是常驻开销**，4 个工具约 400 token，每轮都付
2. **有依赖的工具必然串行**，串行比并行贵 58%

## 七、结论

1. **循环的五个点**：回填 assistant、穿过 Messages 拿调用、按无请求判终止、按名分发、绑定 CallId
2. **工具执行失败要当结果返回**，不能让异常打断整个对话
3. **步数保护触发时，之前的钱不退** —— 上限要合理，生产上应该降级而不是抛异常
4. **有依赖的工具必然串行**，成本比并行高 58%
5. **合并多个问题会让模型变浅** —— 省钱但漏答案，且不报错
6. **一个请求只做一件事**，复杂任务由代码拆分，不指望模型一次搞定
