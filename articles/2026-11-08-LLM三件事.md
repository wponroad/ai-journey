# .NET 后端视角的 LLM 三件事

> 草稿 · 2026-11-08　作者：十年 .NET 后端，转 AI 应用第 12 天
> 说明：所有数字都来自我自己的实测，模型是本地 qwen3:8b 和云端 deepseek-flash。

---

我做了十年 .NET。判断一个接口对不对，我有一套用了很久的标准：返回 200，字段对得上，格式没问题，那就算对了。出错了它会给你 500，或者直接抛异常，日志一查就知道断在哪。

这套标准，在这一周里被推翻了三次。

---

## 一、它不报错，但它是错的

上周五晚上，我在自己机器上跑 qwen3:8b，问它：你是本地模型还是云端模型。

它说：**我是通义千问，部署在阿里云的云端服务器上，可以联网访问。**

它跑在我那张 RTX 2060 上。

我一开始觉得挺逗，后来想了一下，这个其实是生产上最麻烦的地方。HTTP 200，JSON 格式完全正确，中文通顺，逻辑自洽——**所有我用来判断"接口正常"的信号都是绿的，只有内容是假的。**

更麻烦的是它可复现。我把温度调到 1.5 再问一遍，它又编了，而且编的是同一个东西：

> 我是通义千问，是通义实验室自主研发的超大规模语言模型，部署在阿里云的云端服务器上

换个参数再问，还是那句。**它不是在随机胡说，它是在滑向训练数据里最熟的那个模板。**

这一下我就明白了它跟传统接口不是一回事。我们做后端的，接口 200、字段都对，那就算对了，出错它会抛异常。这个东西是 200、格式也对，但内容是假的。你 try-catch 根本兜不住它。

### 同一类坑还有第二个

我写了个成本计算器，需要设输出上限。参数传了 20，跑出来 217 个 token，句子完整，一点没被截断。

代码没错，我逐行看过。后来抓包才发现：**上层库发出去的字段名是 `max_completion_tokens`，而服务端只认 `max_tokens`。**

字段名对不上，服务端就不认识它，直接忽略——不报错，不警告，返回一个完全正常的结果。

这件事比幻觉更阴，因为它连"内容是错的"都看不出来。**你以为限流了，其实没限；你以为账单是 20 个 token，账单按 217 收。**

### 后来我怎么防的

**第一件事是给模型一个人设。**

我最开始没写 System Prompt，模型不知道自己是谁，只能从训练数据里挑一个最眼熟的自我认知。加了一句二十个字的话之后：

| | 系统提示词 | 它的回答 |
|---|---|---|
| 之前 | 无 | 我是通义千问，部署在阿里云 |
| 之前 | 无 | 我是由 **OpenAI 开发的 ChatGPT** |
| 之后 | 「你是我本地AI小助手」 | 我是你的本地AI助手 |

**一句二十字的话，把三轮幻觉全摁住了。**

机制不神秘：它不改模型的知识，只改上下文里的前提。模型是"接着往下说"的机器，你给它"你在本地"这个前提，它就不再往那个高频模板上滑。

**第二件事是别信"输出看着对"。**

设了 `max_tokens` 却不生效，唯一可靠的线索是返回里的 `finish_reason`：`stop` 表示模型自己说完了，`length` 才是被强制截断。**设了上限却拿到 `stop`，就说明参数没传到底层。**

这跟我们查线上问题是一个路子：不看表象，看服务端给的信号。

**我还没搞明白的**：为什么有些场景下加了系统提示词它还是偶尔跑偏。我试过的几个办法（加强措辞、把设定放最后、重复一遍）效果不稳定，这个得再摸。

---

## 二、它不记得你，是你在记

这个发现比第一个更颠覆我的直觉。

我一直默认多轮对话是服务端在记。就像 session，服务端存一份，客户端带个 id 过去就行。

不是。**服务端完全无状态。它不记得你上一句说了什么。**

所谓"它记住了"，是你每一轮都把全部历史重新发了一遍。

我做了个测试，三轮对话，看输入 token 怎么变：

| 轮次 | 输入 token | 我说了什么 |
|---|---|---|
| 第 1 轮 | 61 | 记住，我叫张三 |
| 第 2 轮 | 97 | 我叫什么名字？ |
| 第 3 轮 | 122 | 我今年多大了？ |

**第 2 轮我只问了五个字，但输入涨了 36 个 token。** 涨的全是历史。

这就解释了为什么"聊得越久越贵、越慢"——不是模型变笨了，是你每一轮都在把前面所有内容重新付一次钱。

### 但这里有个反转

我又跑了一组，看服务端返回的用量明细，发现里面有个"缓存命中"的数：

| 轮次 | 输入 | 缓存命中 |
|---|---|---|
| 1 | 61 | 3 |
| 2 | 97 | **61** |
| 3 | 122 | **97** |

**第 2 轮的命中数，正好等于第 1 轮的输入数。第 3 轮等于第 2 轮。**

这是前缀缓存：你这次发的开头只要和上次一样，那段就不重算。命中部分的价格只有未命中的 **1/50**。

所以第 2 轮的成本（0.000077 元）比第 1 轮（0.000146 元）还低——**尽管输入多了 36 个 token。**

> 所以"聊得越久越贵"这句要修正：**多轮对话的成本不是线性涨的。历史确实要付费，但只按 2% 的价格付。**

### 这件事的工程含义

如果让我给客户做一个带对话的功能，我不会再想"上下文交给模型管"，而是**上下文是我的数据结构**：

- 历史存在我这里，存在数据库或内存里
- 什么时候截断、什么时候做摘要，是我的策略
- 每一轮花了多少钱，我可以精确算出来

这个认知转变挺大的。**"上下文"不是模型的能力，是应用的责任。**

**我还没搞明白的**：缓存的有效期到底多长、什么条件下会失效。我只验证了"前缀一致就命中"，具体规则还没摸清，这直接关系到成本预估准不准。

## 三、抽象是免费的，适配不是

第三个坑最隐蔽，因为它连错都不算。

我用的是微软的 `Microsoft.Extensions.AI`，一套把各家模型抹平成同一个接口的库。本地 Ollama 和云端 DeepSeek，代码一行不用改，只换配置里的地址和模型名。

这个体验确实好。好到我一度以为**换 provider 就像换个数据库连接字符串一样**。

直到 `max_tokens` 那个坑。

同一份代码，同一份参数，在两家服务上都不生效。原因是上层库跟的是新规范（`max_completion_tokens`），而这两家的兼容层实现的是旧规范（`max_tokens`）。

我后来又翻了 DeepSeek 的官方文档，发现更狠的：

| 参数 | 实际行为 |
|---|---|
| `temperature` | **思考模式下不生效** |
| `top_p` | 非思考模式下**恒为 1.0，传的值被忽略** |
| `max_tokens` | 支持 |
| `frequency_penalty` / `presence_penalty` | **已废弃**，传了也没有任何效果 |

这些不是 bug，是厂商明写在文档里的取舍。**但接口不会告诉你。**

### 所以抽象层到底抹平了什么

我现在的理解是：**它抹平了"怎么调"，抹不平"能调什么"。**

| 抹平了 | 没抹平 |
|---|---|
| 请求格式、鉴权方式、流式协议 | 参数支持度 |
| 返回结构、错误码的大类 | 能力上限 |
| 换 provider 时改配置 | 计费规则、缓存策略、思考开关 |

这就是为什么我后来不再默认"参数一定生效"，而是每次都验证一遍：改完之后看 `finish_reason`，看 `usage`，对不上就是没生效。

### 这件事指向一个更大的判断

如果只是自己写个小工具，抽象层够用了。

但如果要给客户交付一个"能接多家模型"的系统，你需要的不只是抽象，**是一层知道"这家支持什么、那家不支持什么"的适配层**——参数要按 provider 转换，能力要提前探测，计费要按各家规则算。

这也是我下一步要做的东西。

---

## 最后

这周下来，我最大的变化不是学会了什么新东西，是知道该怕什么。

- 怕"跑通了"这三个字——它不代表对
- 怕"我知道这个参数"——它可能压根没传到底层
- 怕"换个供应商而已"——参数、计费、能力全都不一样

我现在能做的，不是训练模型，是把模型接进存量系统里，并且知道它什么时候会骗我。

**这三件事，是我目前能抓住的全部。**

后面还有上下文压缩、工具调用、检索增强这些没碰过的东西。慢慢来。
