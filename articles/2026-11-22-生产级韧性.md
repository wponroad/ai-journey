# 给 LLM 调用加一层生产级韧性

上一篇里我说，LLM 最麻烦的地方是"它不报错，但它是错的"。

这一周遇到的是另一个版本：**它不报错，也不工作。**

我把调用链从"能跑"改造成"能扛故障"——加了重试、超时、熔断、降级、计费、可观测性。六天里挖出五个坑，**没有一个会抛异常**。它们全都表现为"配置看起来合理、日志一切正常、功能就是不生效"。

写下来，因为这类问题查起来最费时间：你不会去查一个没报错的东西。

---

## 一、重试的三个参数不是独立的，是一份预算

我最初的配置是这样的：

```
单次超时 12 秒
最多重试 3 次
整体不超过 30 秒
```

看起来处处有保护。实际跑起来，`[retry 3]` 从来没出现过——只有 `retry 1` 和 `retry 2`。

算一下就明白了：

```
12 × 3 + 退避(1 + 2) = 39 秒  >  30 秒封顶
```

第三次重试**根本跑不到**。总超时早就把它掐了。

`MaxRetryAttempts = 3` 在这里是个假配置。它不是"配错了"，是"配了但不起作用"——这两者的区别在于：前者会报错，后者不会。

### 更隐蔽的一层

就算把数字改对，还有个问题：**重试次数和实际调用次数差一**。

`MaxRetryAttempts = 3` 意味着总共执行 **4 次**（1 次原始 + 3 次重试）。我一开始按"3 次调用"算预算，算出来的余量是错的。

### 校验方法

一条公式：

```
单次超时 × (重试次数 + 1) + 退避总和 ≤ 总超时
```

以及一个习惯：**给总超时留 2~3 秒余量**。`12 + 18 = 30` 这种"正好相等"的配置不能用，调度延迟和取消传播会让它提前断。

---

## 二、熔断不打开，是因为你的采样窗口比一次请求还短

第二个坑更隐蔽。

熔断配好了：失败率 50%、最少 4 次调用、采样窗口 30 秒。日志里明明看到 4 次失败，**就是不开**。

我当时怀疑是阈值判断的问题，把参数挨个试了一遍。

真正的原因是时间轴：

| 事件 | 累计 |
|---|---|
| 第 1 次 429（瞬时） | 0s |
| 等 1.1s + 第 2 次超时 | 11.1s |
| 等 0.7s + 第 3 次超时 | 21.8s |
| 等 2.1s + 第 4 次超时 | **33.9s** |

**一次请求从头到尾 34 秒，而采样窗口只有 30 秒。**

第 4 次失败发生时，第 1 次失败已经被滑出窗口。窗口内样本不够，熔断器按规矩选择"不动"——它宁可不动，也不基于太少的数据误判。

改成 90 秒之后，立刻生效。

### 这条经验可以通用

```
采样窗口 ≥ 单次请求最坏耗时 × 你希望几次请求后熔断
```

**熔断的所有参数都必须和"一次请求要跑多久"一起算**，因为它们乘在一起才是样本量。

顺带一个：熔断阈值和重试次数也是乘法关系。`MinimumThroughput = 4` 配 `MaxRetryAttempts = 3`（共 4 次尝试），意思是**一次失败的用户请求就足以打开熔断**。这通常太敏感了——一个用户偶发失败就把整个服务熔断，会影响所有人。

## 三、失败的请求有账单，只是你看不见

这是这一周最重要的发现。

那次熔断触发后，我的日志是这样的：

```
[degrade] 没有产生 token 消耗（请求没真正发出去）
token 输入  / 输出  | 等价云端成本  元
```

账面上是 0。但前面**三次"放行"的真实调用都超时了**——模型可能已经算了 3 秒、生成了 200 个 token、服务端已经计费，然后 10 秒到点被掐断。

### 为什么拿不到账

因为 `usage` 是**响应体里的字段**：

```csharp
var response = await client.GetResponseAsync(...);   // ← 超时在这里抛异常
if (response.Usage is { } u) { ... }                 // ← 从来没执行到
```

**响应没完成，就没有响应体，就没有 usage。**

### 三种失败，账单可见性完全不同

| 故障 | 有响应吗 | 有 usage 吗 | 可能已计费吗 |
|---|---|---|---|
| 429 | ✅ | 通常有或明确没有 | 一般不计 |
| 500 | ✅ | 通常没有 | 一般不计 |
| **超时** | **❌** | **❌** | **可能已经计了** |

**超时是唯一一种"钱可能花了、而你完全不知道"的失败。**

所以那句日志的措辞是不诚实的。"没有产生 token 消耗"听起来像"没损失"，准确说法是"没收到统计，可能已经产生费用"。

### 工程上怎么办

三层，从便宜到正确：

1. **日志措辞诚实**：区分"零消耗"和"没拿到统计"
2. **估算输入侧**：输入 token 是确定的（prompt 固定），超时时按输入价记一个下界
3. **服务端记账**：请求带 `request-id`，服务端记账、客户端对账

第三条是唯一正确的做法。它也是"凭什么相信 `usage` 那个数字"这个问题的答案——**不相信任何一方，用两个独立来源交叉验证。**

## 四、降级做得越好，故障越难被发现

降级最初的版本是这样的：

```csharp
return "抱歉，服务暂时不可用，请稍后再试。";
```

**那不是降级，那是换个说法报错。**

真正的降级是"用更笨的办法把事情办了"。在这个订单查询项目里，模型干的活只有两件：识别意图、抽参数。订单号是 `[A-Z]\d{8}`，商品编号是 `SKU-\d{3}`——正则比模型稳，而且永远不会挂。

```csharp
var orderNo = Regex.Match(question, @"[A-Z]\d{8}").Value;
if (orderNo.Length > 0)
    return _orderService.GetOrder(orderNo);
```

这样做的效果是：模型全挂的时候，用户问"订单 A20261109 什么状态"，还是能拿到真实的"已发货，128.50 元"。

### 但这里有个反噬

降级做得越好，**故障越难被发现**。

模型挂了三天，用户一直在用规则兜底，没人报错，监控一片绿——直到有人问了一个正则答不了的问题。

所以我给每一行账都加了一个状态字段：

```csharp
reply.IsFallback ? "fallback" : "ok"
```

**不能把降级记成"成功"。** 混在一起的话，"成功率 100%"会一直挂着，而背后可能全是正则在答。

### 比降级更根本的一层

降级解决"怎么兜"，但解决不了"该优化哪一步"。

我用 OpenTelemetry 把一次对话拆开之后，看到的第一个数字就把我的直觉打翻了：

| 项 | 耗时 | 占比 |
|---|---|---|
| 模型两次调用 | 11.68s | 54% |
| **缓存查询** | **5.75s** | **27%** |
| 没有 span 覆盖的空隙 | 4.24s | 19% |

**缓存查询比模型还慢**。原因是 embedding 模型 1.2GB，第一次调用要加载权重——冷启动。

而那个 4.24 秒的"空隙"是另一个问题：缓存未命中写回时，**又把同一句话 embed 了一遍**。

两个问题都修掉之后：

| | 优化前 | 优化后 |
|---|---|---|
| 总耗时 | 21.67s | **11.96s** |
| 模型占比 | 54% | **99%** |

**优化后，模型成了唯一瓶颈（99%）。**

这个比例变化比"省了 45%"更有意义——它回答了"优化到哪一步为止"：

> 当模型占 99%，再优化代码，收益上限只有 1%。

## 五、最后说一个方法论

这五个坑有个共同点：**代码都编译通过，日志都正常运行，功能就是不生效。**

所以我给自己加了两条规矩：

**1. 涉及数值的配置，先算一遍再写**

超时、重试次数、采样窗口、阈值——这些数字不是独立的，它们乘在一起才是真实行为。写之前先在纸上算一遍乘积。

**2. 涉及数值的判断，先量再说**

我以为"订单 …109"和"订单 …110"的语义相似度大概 0.7，实际是 **0.9892**——比同义改写的 0.9543 还高。

我以为"任意两句无关的中文"相似度接近 0，实际是 **0.4976**。

三个预估全错，而且方向一致：低估基线、高估区分度。

**在这类问题里，"感觉差不多"是负资产。**

---

## 结尾

我现在能做的，不是训练模型，是把模型接进存量系统，并且知道它在什么情况下会骗我、什么情况下会悄悄不工作。

这一周加的这层东西——重试、超时、熔断、降级、计费、可观测性——它们不产生任何业务价值，只在出事的时候证明你还站着。

但恰恰是这些，决定了这个东西能不能交给客户。
